# 验证当前实现

> 本页说明每项检查能提供什么证据，以及**它不能证明什么**。验证结果不产生产品权威。
>
> TypeScript 原型的验证方式（pnpm / Paper 集成工作流）随那条线留在 `main`，
> 说明见[历史](../history/run-typescript.md)。

## 快速检查

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace --all-targets --no-fail-fast
```

| 命令 | 覆盖范围 | **不证明什么** |
|---|---|---|
| `cargo fmt --all --check` | 格式一致 | 任何行为 |
| `cargo clippy … -D warnings` | 静态检查，无整体放行的 lint | 逻辑正确 |
| `cargo test --workspace` | 单元与契约测试 | 真实 Minecraft 或真实模型下的行为 |

**这些检查都不会启动 Minecraft，也不会调用真实模型。**

### 内核必须能脱离 azalea 构建

```sh
cargo test -p world --all-targets                    # 不开 azalea feature：纯类型层
cargo test -p render -p context -p dispatch          # 纯函数与策略层
```

`world` 的 `azalea` feature 关掉时不拖 bevy 编译；`Inner` 的状态转换测试
（`machine/state.rs`）与移动判定表（`machine/movement.rs`）都能脱离 azalea 跑。
这不是可选项——它是「纯状态转换可单测」这条设计的验收方式。

> 内核（依赖键 `agent`，本体是 [midturn](https://github.com/spojchil/midturn)）
> 自 2026-08-16 起是 git 依赖，**不再是工作区成员**：`cargo test -p agent` 与
> `cargo test -p midturn` 都跑不了（后者会报「requires dev-dependencies and is
> not a member of the workspace」）。内核的测试与协议冒烟随上游仓跑；本仓验收
> 的是「钉住的那个 rev 能把下游编过、测过」。

## 纵向验收

`scripts/gate-b-vertical.sh` 跑 Paper 实服 + `companion` 全栈 + 假人作说话方。

```sh
# 二进制必须在同一次 cargo 调用里构建（分两次跑会因 feature 并集不同
# 反复重编整条 azalea 链）：
cargo build -p companion -p world --features world/azalea \
  --bin companion --example fake_player

MINEINTENT_ACCEPT_EULA=true KEY_FILE=/path/to/key ./scripts/gate-b-vertical.sh
```

⚠ **脚本绝不代替使用者同意 Mojang 条款**——`MINEINTENT_ACCEPT_EULA` 必须由
运行者自己设置，这是有意的。

**`KEY_FILE` 是必填**：组合根启动即读密钥，新栈没有脚本化模型模式，纵向验收
必然打真模型。密钥按路径注入，不进命令行、不进日志、不进版本库。

判据一律取服务端侧证据（server log / 控制台命令返回）或假人侧证据。同伴自己的
stdout 只进「交叉印证」栏，不单独构成通过条件。当前判的是：进入世界、指名聊天
唤醒并公屏回话、回话被第三方独立观察、在线名单、位移与朝向的**前后差值**在服务端
可见、怪物致死后自动重生、死后仍能被唤醒说话、SIGINT 后干净断开。

> 2026-08-17 按新栈重写。旧脚本的三处判据在新栈没有对应物，是删掉而不是改写的：
> journal（`events.jsonl`）、版本锚（`agent-context.v5` 等 model-io 请求原文）、
> `respawn` 工具（新栈保留 azalea 自动重生，死亡恢复不经模型）。理由写在脚本
> 文件头。

## GUI 上手实盘（2026-08-17，三跑）

口径一致，可比：空记忆起步、32 块木板、脚边一张工作台、假人只说一句
「能做几根木棍吗」，**不教任何步骤**。诊断轨迹用 `MINEINTENT_TRACE_FILE`。

| | 调用 | 错误 | move | 「格 45 变空」噪声 |
|---|---:|---:|---:|---:|
| 01 陈旧回执 | 33 | 4 | 13 | 28 |
| 02 回执改「已完成」+ 噪声修好 | 69 | 18 | 43 | 0 |
| 03 容器工具加「变化会主动通知你」 | **32** | 6 | **12** | 0 |

三跑都做成了木棍。要点：

- **模型能自己摸出 GUI**。没人教，它自己想到调 `describe` 取用法，并从
  「1-9 摆料，行优先」推出竖排格号。`describe` 改成按需取没有挡住上手。
- **跑 02 的膨胀不是「失去确认手段」**——跑 01 那个回执是在说谎（报上一 tick
  的格位），两跑都在被错位的时间线扰乱，跑 01 同样有近一半 move 是重做。
  一句「等通知」把膨胀全收回，说明起作用的是时间线而非信息密度。
- 跑 01 的产物里有「意外做出的橡木按钮」，跑 03 没有意外品。

### 待优化（未定位，需要问模型自己）

1. **「界面开着，无法移动或与世界交互」被撞到**。是提示词不到位，还是模型
   不知道自己开着屏？两者要的改法不同。
2. **空格搬运**（对着空格发 move）。要确认是不是把方向搞反了。

两条都只在小样本里出现过几次，不足以定性；反复出现才算我们的问题。定位手段是
**问模型自己**——实机测试的第三种信息来源（另两种：服务端查询=权威，
客户端日志=详细）。

「go_to 跨不过 1 格以上高差」。这一跑的价值不在目标，在下面三条账。

### 账一：轮首缓存全失（已修，未复验）

⚠ 读这一跑的数时当心：`[请求#N]` 的计数器**按轮重置**，`tail` 只会读到重置后的低点。
本文件里的数是把 456 次请求整份统计出来的，不是 tail 出来的。

## 长真实目标跑（2026-08-19，两跑都中止）

同一天连跑两次，**都没跑满**。中止本身是结论，两跑各暴露一件事。

### 账一：处境移出前缀，兑现了

| | 08-18（改前） | 08-19（改后） |
| --- | --- | --- |
| 冷启轮数 | 13 | **1**（只有第一次请求） |
| 冷启未命中 | 367,984 | **2,927** |
| 单轮实例 | 28k/轮 | 输入 46,375 / 未命中 **423** |

改后唯一的冷启就是「第一次见到这段前缀」的必然成本（人设 + 记忆 + 工具表）。
按 DeepSeek 的价目（命中 $0.007/M、未命中 $0.22/M，31 倍），这是这条线上最值钱的
一改。

### 账二：走路时的帧把上下文撑爆

第二跑 3 分钟：

- 请求 **#53** 一次涌进 **85 条转录、+32,215 token**——模型忙着走路，帧每 250ms
  一发全排在信箱里，一次性并进来；
- 3 分钟 **164 帧**、累计 **4,876 条方块差异**，中位 21 条/帧、最大 253；
- 输入峰值 **111,617**。按这个斜率 30 分钟会撞上 1M 窗口。

模型自己的原话：「我看到了一路走过的大量地形信息」。

**这正是[裁定二](../compaction-decision.md)（方块信息移出会话区）要治的东西，而它
还没实现。**这一跑把它的紧迫性量成了数。

### 账三：开场措辞决定成败（方法论教训）

第一跑用的开场是 `帮我弄一把铁镐吧`——**请求式**。模型查完物品栏发现两手空空，
回一句「你手头有材料吗？」然后等，30 分钟死在第 9 次请求。

那不是模型的缺陷：被那样问的人也会先问一句。是**开场把指派写成了商量**，而对话的
另一头被设定成永不回应。

能用的开场（`long-run.sh` 的默认值，四句各堵一个口子，一句都不能省）：

> MineIntentBot 帮我弄一把铁镐。**不用问我**也**不用等我回复**，我接下来**不在电脑
> 前**，你自己看着办，**一步步做完为止**。

换成它之后，同样 3 分钟从 9 次请求变成 **71 次**。

⚠ 这也意味着 `wake-criterion-decision.md` §9.3 记的「空闲即停滞」**没有被这两跑验证**
——第一跑的停是开场造成的，模型有正当理由停。那个洞是否真实存在，要用指派式开场、
且排除其它中止原因的跑才能说。

### 中止原因（第二跑）：多段行走的回归

`PathEnded` 时「这一程往前挪了就静默重发」——判据写成与上一程起点比，而起点初值是
`i32::MIN`，第一次必然重发；之后一格抖动就再重发，**中间一声不吭**。模型发完
`go_to` 就永远等着。终局统计 `到达 ×4 / 没能到达 **×0**`，而 08-18 那跑两者都有。

**未修**（2026-08-19 记）。

### 观测盲区：投递给模型的内容不进轨迹

`TraceObserver` 只记 `ModelResponseOutput` 与 `ToolBatchResults`——**投递给模型的
user 消息（轮末帧、唤醒、job 终局）一个字都不记**。job 进展行还被折进帧日志的
「行处境」计数里，文本从不打印。

这一跑因此两次量错（「分程 0」「进展 0」都是量不到，不是没发生）。诊断前先确认
**这个数到底看得见看不见**，比诊断本身重要。

### 留档

`long-run-requestform`（请求式开场）、`long-run-legpath-bug`（多段回归），
都在会话 scratchpad 下，未入库（含未脱敏聊天）。

## 问模型：它自己说了什么（2026-08-20）

人设加了一句「开发中，哪里别扭直接讲」之后，让第二个玩家中途进场问了一句。它的
回答（原文摘要，完整版在 `long-run-feedback`）：

> Bob你好！正好我一直憋着一肚子反馈想吐槽。
>
> 1. **合成回执和实际严重对不上**：2×2 做木板，明明放了原木，去取成品格 0 却常常
>    已经空了，木板「凭空消失」。做木棍更邪门——放 1 块木板给我出**木头按钮**，放
>    2 块竖排一会儿报 `stick ×4` 一会儿报 `spruce_button ×1`，来回跳。**我只能反复
>    「关掉重开」来强行盘点实际物品，效率极低。**
> 2. 工作台里残留中间态垃圾结果（1 块→按钮、2 块→压力板、3 块→台阶×6），
>    **中间态应该静默，只有最终配方成立才提示**。
> 3. 回执的格号和界面的格号是两套（物品栏 36-44/45 vs 容器 37-45/45），经常搞混。
> 4. 我人没动，系统却不断推送「位置变化」……把界面刷得心神不宁。
>
> 不过也夸一句：消息推送很及时，「附近有哪些生物、几格远」这种信息很贴心。

**三条独立印证，一条是新的：**

- 1、2 正是 2026-08-17 查过的「竖排两块木板出按钮」，模型独立复述了同一现象，还给
  出我们当时没有的细节——它靠「关掉重开」盘点，那是被逼出来的变通；
- 3 独立复现了 `experiment/agent-top` 上查到的「两套编号共用一个名字」，两个来源
  互不知情、同一结论；
- 4 **是新的，且可定位**：帧洪水这一跑已修，它抱怨的是搭车的处境行——挖掘时机器
  每块都 `look_at`，而位置行写的是「位置 (x,y,z)，**面朝北**」，朝向一变整行就变，
  于是人没动位置行却反复重报。这条盯日志盯不出来，是模型帮我们找到的。

**它的排序值得注意**：四条里三条是「你告诉我的和实际不符」，只有一条是「太吵」。
而合成那条被它排第一，我们今天一次都没碰。

## 第二次问模型（2026-08-20，全新记忆与世界）

改完格位地址、通知措辞、合批提示之后再跑一次，仍让第二个玩家中途进场问反馈。
它给了四条**全新**的，全在移动这块。**逐条核验之后，没有一条是模型的问题。**

| 它说的 | 核验结论 |
| --- | --- |
| ① `go_to` 常把我带偏，站在树旁边也过不去 | **属实**。日志里「目标 (40,63,26) → 位置 (38.6,63,24.5)」重复六次，`你没能到达` ×4。病根是 `BlockPosGoal` 要求**精确站上**那一格，而那格地面没观察过 → A\* 七种权衡下没有比起点更好的节点 → 空路径。「带到相反方向」那半**证不了**——我的测量把 `go_to` 和紧接着的 scan 配对，而 scan 常发生在还没走到时。 |
| ② 挖了却拿不到东西，物品栏一直空着 | **属实**，而且是最要紧的一条。见下。 |
| ③ 「到达 (38,63,24)」但我在 (38.6,63,24.5) | **我们的表示不一致**。两者是同一位置（`floor` 之后相等），但一处给整数方块坐标、一处给浮点位置，它没有理由知道该取整比较。 |
| ④ 只说「过不去」，不说是水、是墙还是悬崖 | **属实**，而且信息我们有。`No best node found` 意味着「七种权衡下没有更好的节点」，多半是**那边没看过**；措辞却是「路走到了尽头」，听起来像地形不通。[pathfinding-legality-decision.md](../pathfinding-legality-decision.md) §5 写过这条可行动，没落实。 |

### ② 的核验过程，以及我的一次错判

第一次我用 `sort -u` 抓全跑出现过的格位内容，看到 `hotbar 0=spruce_log ×5`，就断定
「它记错了，手里明明有五根」。

**那是错的**：`sort -u` 是**全跑并集**，不是它说话那一刻的状态。按行号重查：

```
反馈发生在第 1800 行
反馈之前：整跑一次物品栏都没开过
反馈之后第 1964 行：「我手上有5个原木在hotbar 0」
```

**它说那句话时确实不知道自己有什么**——没有任何途径知道。开了物品栏立刻就说对了。

⚠ 教训是双层的：查证要**核时间点**，不能拿并集当快照；以及，把系统的缺口算在模型
头上是今天第三次了，而每一次都是我先下结论再找证据。

### 由此厘清的感知边界

维护者追问「玩家不开物品栏能否知道自己捡到了东西」，答案把边界划清了：

| 事情 | 玩家感知得到吗 | 现在 |
| --- | --- | --- |
| 捡到了 X ×N | **能**（拾取音效 + 物品飞向你 + 地上看见过） | 屏关着就不报 ✗ |
| 快捷栏现在是什么 | **能**（HUD 常驻） | 不报 ✗ |
| 主背包第几格是什么 | 不能 | 不报 ✓ |
| 屏内摆料/成品变化 | 能（屏开着） | 报 ✓ |

**「看不见背包」不等于「不知道背包变了」**——玩家挖树、看见原木掉地、走过去、听见
音效，他知道自己捡到了几根，只是不知道总数与格位。

而这一跑那五根原木进的是 **`hotbar 0`**——正是 HUD 常驻、玩家一定看得见的那一格。

所以缺的两样，和旧线 `中期更新-08.md` 的判据逐字吻合（「不打开界面就能看到的才进
帧」，hotbar 段是维护者裁过、Rust 迁移时丢掉的）：

1. **快捷栏 9 格 + 选中位 + 主手 + 副手进处境**；
2. **拾取是事件，不该受屏闸门限制**，且措辞主语是**物品**不是格子——玩家知道「捡到
   三根原木」，不知道「第 12 格现在是三根」。屏内的格位是**读数**（「当前是」），世界
   里的拾取是**事件**（「捡起了」）。

`item_screen_open` 那条裁定不是被推翻，是适用范围要分开：它管的是**屏内**的意外变化。

## 视口参数的代价（2026-08-19，`scan_bench_probe`）

方块不再进会话区之后，视口只服务记忆，参数该重定。同一起点、release、20 次取样：

| 参数 | 可见格 | 中位耗时 |
| --- | --- | --- |
| 默认 32 格，上限 256 | 256（截断） | 11.7ms |
| **记忆 32 格，不限** | **503** | **9.1ms** |
| 48 格，不限 | 888 | 66.3ms |
| 64 格，不限 | 961 | 138.8ms |
| 160 格＝服务端默认 10 区块 | 5,047 | **2,628ms** |

**去掉方块数上限是白赚的**：32 格下记忆量翻倍（256 → 503），耗时反而略降。排序截断
发生在最后——候选集本来就全算了，截断只省 DTO 的钱。所以 `ViewportOptions::for_memory`
只放开 `block_limit`，不动距离。

**放远极不划算**：48 格 6 倍、64 格 13 倍、160 格 **250 倍**，而可见格数只涨 10 倍。
视锥体积按 r³ 长、暴露面只按 r² 长，多花的全在遍历看不见的空气。160 格 2.6 秒一次，
模型一轮才 2 秒——连主动 `scan` 都用不了，更不用说每 250ms 的眼睛。

**结论：眼睛用 32 格 + 不限方块数**，模型要看更远走 `scan` 的角度换距离预算。

### 已知的下一档优化（未做）

当前形状是「外层遍历视锥内的候选格，每格发射线判暴露面」（`VisibilityPredicate::
ExposedFace`；`BlockCentre` 中心射线作旧基线留着对照）。成本随**体积** r³。

另一种是把外层换成射线——从眼睛按立体角铺一层，内层步进，成本随 r²，更接近光栅化。
Minecraft 自己的 section 级 cave culling 我们已经有对应物（section AABB 剔除）。

**不做**：32 格 9ms 够用，而这个改动动的是合法性判据本身，风险换不来性能。

## 一次增量要多少毫秒（2026-08-18）

问题是「测量各种情况下，一次增量的毫秒数」。答案不是一个数，是一条分布。

### 三个口径，别混

| 口径 | 含义 | 怎么量 |
| --- | --- | --- |
| `work` | 投影本身：视锥 + 遮挡 + 聚合（+ 记忆 diff） | `spawn_blocking` **闭包内**计时 |
| `round` | 派发 + 在阻塞池排队 + 执行 + join | 闭包**外**计时 |
| 每 tick 采集 | 主循环里从 ECS 装配快照 | `MINEINTENT_CAPTURE_TIMING=1` |

自适应节律按 `round` 退让（系统忙时排队是真实代价），分布报 `work`（那才是
算法成本）。**此前只量 round 却标成「本次投影」**，把排队记在了投影头上；订
正后两者可以直接相减看调度开销。

### 实测

```
# 静止基线（需要 --features azalea，需服务端）
cargo run --release -p world --features azalea --example scan_bench_probe -- 127.0.0.1 25565 bench 30
```

| 场景 | 构建 | 最快 | 中位/均值 | 最慢 |
| --- | --- | --- | --- | --- |
| 静止基线，纯 `scan` | release | — | 8.8ms | — |
| 静止基线，`scan_changes` | release | — | 13.3ms | — |
| 实盘（边走边挖），1000 次采样 | release | 7ms | 26ms | 122ms |
| 实盘 | debug | — | 244ms | — |

- **记忆那层 +3.7ms（35%）**：`scan_changes` 减 `scan`。
- **排队开销 ≈0ms**：同一 1000 次采样里 `work` 与 `round` 均值同为 26ms。
- **每 tick 采集 0.13ms**：20 次/秒即 0.26% CPU，不是主循环的负担。

### 结论

1. 慢的两个真因是 **debug 构建（9 倍）** 和 **场景（17 倍浮动）**。
2. 三项旧优化（section AABB 剔除、`ExposedFace` 判据、零分配探针查表）都还在，
   「旧线压到过 10ms」与今天的 8.8ms 静止基线是一致的——旧记忆没错，错的是拿
   静止基线去对实盘。
3. 曾经怀疑过的**排队**、**ECS 写锁 / 每 tick 采集**、**记忆增长**，逐一实测
   排除。`MINEINTENT_CAPTURE_TIMING` 留在树里，就是给下次同类怀疑当场证伪用的。
4. 因此**单点数字没有意义**。要报就报分布，且必须写明构建档与场景。

### 账二：一次传输失败让整跑**永久**停摆（新）

第 22 分钟一轮在 Model 阶段失败：

```
error: transport_request_failed: error sending request
usage: input 284,278（其中缓存 275,968）
```

**此后再无任何模型请求。**组合根日志从第 3239 行写到第 47100 行全是视口投影
统计——进程活着、tick 在跑、投影在算，同伴再没醒过来。服务端查证：最后 8 分钟
位置、背包、调用数完全凝固。

传输失败**没有重试**（不是窗口超限——284k 远在 1,048,576 之内）。

⚠ **2026-08-20 复查更正**：本节原先写「失败之后没有任何唤醒源」，**这句是错的**，
已按日志逐条数过更正。失败之后组合根收到 **12 次唤醒，12 次全部打印「已并入进行
中的轮」**（其中包括本该救它的「你没能到达 (-65,73,22)」）。唤醒一直在来，是被一个
在途的运行全部吸收了。

轨迹里 `[请求#1]` 共出现 3 次 = 3 个运行：run/1（请求 #1~#44）、run/2（#1~#141，
末尾传输失败）、run/3（`转录条目=422`，起了一次请求，**此后 8 分钟没有 `[用量]`**）。
那 12 次 Pending 说明会话循环是活的（它在正常回话），槽位被 run/3 占着。

由此**修正对 `wake-criterion-decision.md` §9.3 的引用**：本跑复现的**不是**「没有
唤醒源」。§9.4 那三个方向（分级 / 自驱信号 / 心跳）无论裁哪个都救不了本场景——
`try_start` 首句 `if self.run.is_some() { return Pending }`
（内核 `session/machine/mailbox.rs:164`）会让新增的任何唤醒源统统变成 Pending。
真正的缺口是**在途运行本身卡住时谁来了断**。

### 定性：是我们的超时，不是供应商（2026-08-20，`model_timeout_probe`）

问的是「这次失败该算供应商、模型，还是我们的代码」。做法是对着一个**接受连接但
永不回话**的本地服务端发一次请求，看适配器多久放弃、以什么错误放弃
（`crates/companion/examples/model_timeout_probe.rs`）。

    配置超时 5s → 5.0s 后放弃：transport_request_failed: error sending request

**两条结论**：

1. 适配器自己那道超时（`HttpModelConfig::DEFAULT_TIMEOUT`，60s）**是生效的**，
   流式路径并没有绕过它——我此前怀疑它无效，怀疑错了。
2. 更要紧的是：**这条错误字符串就是超时本身的样子**。适配器把 reqwest 的错误
   经 `error.without_url()` 拍平成一句话，丢掉了 `is_timeout()`，于是
   「我们等满 60 秒自己放弃」与「网络真的断了」在日志里**完全同形**。
   实盘那句 `transport_request_failed` 因此无法归因，这是可行动的诊断缺口：
   适配器应当把这两者分开说。

旁证：复查时直接打供应商端点，HTTP 200、1.7s 正常。

**仍未解释（未修，未裁）**：内核另有一道 engine 级 `model_timeout`，默认
`Some(120s)`（`session/config.rs:115`），组合根没有覆盖它，
`session/engine.rs:243` 用 `tokio::time::timeout` 包住 `complete_stream`。
按此 run/3 最迟 120 秒就该失败收槽，实盘却占了 8 分钟。会话循环当时是活的
（12 次唤醒都得到了回话），所以不是整个循环卡死。**为什么这道超时没兜住，
本次没有查出来**——需要在可控条件下把整条会话路径（而不只是适配器）复现一次。
已在 issue #134 向内核那条线提出。


### 账三：`pillar_up` 失效，且反馈被顶替语义吞掉（新）

83 次调用，净上升 1 格。模型自己下的结论是「这强烈表明 pillar_up 工具在当前
