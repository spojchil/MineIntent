## 1. 已裁：轮末帧装什么

### 1.1 判据

来自旧线 `中期更新-08.md`（分支 `origin/experiment/rust-viewport-incremental`，
§ 开头），维护者确立、由 `standingOnBlock` 那次裁决推广而来：

> **不打开界面就能看到的才进帧。**帧 = 被动推送；主动读取（view、未来的关注/
> 历史工具）与之并存不冲突。

这条判据是**双向**的：原版 HUD 上看得见的必须进帧；需要开界面才看得见的必须留在
界面里。`standingOnBlock` 正是因为反向不成立（「视觉通道白拿」）而被整体删除。

维护者 2026-08-02T14:10:38 逐条给出（会话转录
`d0df19c7-9768-4e4c-9bf9-248b0a866992.jsonl` 第 16069 行，`origin.kind=human`）：

```
帧，暂定为，未读的聊天记录数，不是内容
听觉

坐标，朝向
血量，饥饿度，盔甲值，盔甲韧性。为0时可以不显示。
部分或者全部药水效果，如反胃，饥饿，凋零，因为这些不需要进物品栏就可以看到。不过这里可以先不考虑实现

  目前就考虑到这些，当前可能有些不要求现在做
这里的设计，看看能不能像工具注册的那种一样，方便后续修改，如果不适合。不强求
```

同日 14:58:21（第 16081 行）给出「为什么只有快捷栏、不是整个物品栏」的理由：

> 背包或者说物品栏……这是一个 gui 界面，会阻塞或者停止某些动作。而且，打开物品

> 我好像混用了帧和 tick。现在把我们的工具调用的项目的帧成为轮末帧。单说帧，就是
> 原版的 tick。

2026-08-20 维护者追问「玩家不开物品栏能否知道捡到了东西」，把感知边界补齐（见
`642f8fb` 提交信息）：看不见背包不等于不知道背包变了——拾取有音效、有动画、东西
是自己看着掉的。故**拾取是事件**，不受屏闸门限制，且措辞主语是物品不是格子。

## 2. 当前实现与清单的差距

当前没有「轮末帧段」这一层。上述内容分散在 `render::render_situation_lines`
（称作「处境」）与增量帧两处。逐项对照：

| 已裁段 | 现状 |
|---|---|
| viewport | 在帧上 ✅（2026-08-20 起方块信息不进会话区，改由 `blocks` 工具查记忆库，见 `docs/compaction-decision.md`） |
| pose | 处境 `Position` 行 |
| status | 处境 `Vitals` 行；**盔甲值缺失**（`SelfState` 无该字段，盔甲仅存在于物品栏 5–8 号格） |
| effects | 揉在处境 `Vitals` 行内，非独立段 |
| chat | 处境 `Unread` 行（只有条数，未落实「内容 + omitted 计数」） |
| world | 处境 `Environment` 行；**且把已判出局的 timeOfDay 放了回去**（`day_period_word`） |
| hotbar | **缺失**。数据齐备：`SelfState.inventory` 有 9 格（菜单号 36–44）、`selected_hotbar_slot`、副手 45 格 |
| sound | **缺失**。数据齐备：`TickSnapshot.sounds` 是 60 tick 窗口且已分三种来源，无任何渲染出口 |
| light | **缺失**。数据也没有：`TickSnapshot` 无光照字段，需机器层新采 |
| 注册式装配 | **未建**。现为 `render_situation_lines` 里的硬编码 `Vec` |

按工作量分三档：

- **已有数据、只差渲染与接线**：hotbar、sound；pose/status/chat/world 属改归属；
- **要拆的**：`world.timeOfDay` 从环境行摘掉；
- **要动机器层、各自独立一轮**：light（新采集）、status 的盔甲值（新字段或从装备
  推算）。光照尤其需要实盘查证——「洞里黑」若失真模型会当真。

「处境」不是已裁概念。全量转录检索（该目录 39 个 `.jsonl`，1187 条

维护者本人给过的分层（2026-07-25T13:11，第 4979 行）是四段且不含处境：

> 分层大概是 / 系统提示词 / 记忆 / 工具信息 / 轮次 …… 你可能问，视口呢，其他环境
> 信息呢…… 视口，只有一个模式 diff，就是普通的工具调用

关键冲突在 2026-08-10。当日 14:04:57（第 41219 行）维护者裁定：

> 而我们就是在这个基础上下文里，放两个东西，系统提示词和记忆，对吧

一小时后 15:09:23（第 41524 行）助手汇报中出现：

> 受保护上下文合一……人设/记忆/处境全在这一段拼，置于请求最前、永不入压缩

维护者在该条之后的回复只涉及压缩语义，对此点零回应、零确认；15:24:06（第 41676
行）他仍在往轮末帧放东西（「世界元信息……选择一下放轮末帧和一个单独的信息工具
里」），从未接受前缀放置。

而这条结构造成的开销，维护者早在 2026-07-25T12:16（第 4850 行）就预警过：

> 然后我似乎发现一个问题，如果 messages[1] user 是易变的话，缓存会不太友好吧

同日 14:31（第 5033 行）给了正确机制：状态帧「**相等于普通的上下文历史，缓存自然
命中**」。

代价在 2026-08-18 兑现：30 分钟 456 次请求，13 次轮首未命中 367,984 token，占全跑
75%（详见 `docs/compaction-decision.md` 与 `docs/guides/validation.md`）。

**注**：`6bd14ec` 已把 `base_context` 改回只有人设与记忆，等于补执行了 08-10 那条
裁定；但「处境」这一中间概念保留至今，本文第 2 节的差距由它承载。
