# 一行代码如何把原型范围固化成另一种产品

## MineIntent `primaryPlayer` 事件详细调查

- **调查基线：** `MineIntent` 仓库 `main@46bcd4d`
- **调查日期：** 2026-07-28，Asia/Shanghai
- **文档性质：** 调查报告，不是产品规范，不是修复方案，也不自动代表维护者接受了本文的全部推断
- **可移植性：** 本文不含外部链接；关键证据以提交号、Issue/PR 编号、文件路径、代码摘录和本地复核命令保存

## 0. 调查判词

本事件不能准确地概括成“Agent 凭空写了一行代码，于是突然发明了另一种产品”。`primaryPlayer`、一名主要伙伴的 v0.1 范围、主要玩家的特殊控制语义，都早于目标代码存在。

更准确的结论是：

> PR #31 没有把一个已经明确的产品决定直接实现出来。它把“第一版主要验证一个玩家”“主要玩家拥有特殊控制语义”和“只有主要玩家的消息值得进入 AI 的认知”三个不同命题，压进了同一个布尔守卫。守卫与同一 PR 中的必填配置、单人测试夹具共同固化了这个选择；后续现场验收、README 和 PR #93 又继续维持并放大了它的实际效果。

目标代码是：

```ts
if (!message?.addressing.addressedToCompanion || !message.sender.isPrimaryPlayer) return
```

它不是产品分叉的创世点，而是产品分叉的**语义编译点**和**可执行否决点**：原先散落在范围、身份、控制和上下文里的假设，到这里第一次成为所有玩家聊天进入模型的路径必须服从的社会准入规则。

截至调查基线，实际运行产品更接近：

```text
一个由部署配置预先指定的中心玩家
+ 该玩家几乎垄断唤醒模型的能力
+ 其他玩家可以作为世界实体被看见，却不能通过聊天进入 AI 的认知
+ 被排除的消息不留在 AI 可查询的历史中
```

而 Issue #109 将下列内容标注为“维护者明确说明、由 AI 助手整理”的当前方向。本文把它作为有明确来源声明的方向记录，而不是维护者逐字谈话稿：

```text
所有游戏内玩家在系统身份上同级
+ AI 自主管理关注对象
+ 未主动通知的公屏消息仍可按需回看
+ 关系由 AI 在自然语言记忆中理解和维护
+ 游戏外管理者与任何游戏内玩家身份分离
```

这不是同一产品的“单人版”和“多人版”，而是两种不同的社会模型、注意模型和权力模型。

## 1. 本调查到底在调查什么

本调查不以“这一行有没有空指针、类型错误或语法问题”为核心。它回答五个更高层问题：

1. 这一行在什么历史上下文中出现？
2. 它把哪些原本分开的产品概念合并了？
3. 为什么它在局部代码审查中看起来完全正常？
4. 它如何在没有继续修改自身的情况下，随着周边系统变化而获得越来越大的产品权力？
5. 为什么多轮 AI 设计、实现、测试和审查没有形成真正独立的纠错？

用户口述的简写是：

```ts
if (sender !== primaryPlayer) return
```

这不是仓库中的逐字代码，但在当前调用方式下，它非常接近真实有效语义。后文会证明，Runtime 永久把 `conversationActiveWith` 设为 `primaryPlayer`，因此主要玩家的普通公屏发言也会被判定为延续对话；非主要玩家即使明确点名同伴，仍会被身份条件挡住。

## 2. 证据纪律：避免本调查重演 Issue #108

Issue #108 初版已经展示过一种危险：仓库文本可以提供一条时间连续、词语相似、彼此引用、看起来极其完整的故事，但这个故事仍可能错误描述维护者真实的思想来源。

因此本文把证据分为六类：

| 标记 | 含义 | 本文允许得出的结论 |
| --- | --- | --- |
| **仓库事实** | 可由当前 Git 对象、代码、测试和本地历史直接复核 | 某段文字或行为确实存在；某行何时进入 `main` |
| **平台快照** | 调查时通过 GitHub 元数据读取的 Issue、PR、评论、时间和统计 | 平台当时记录了什么；不证明物理作者或维护者内心接受 |
| **维护者直接说明** | 用户在本次对话中直接作出的说明 | 可以作为维护者当前判断；仍应区分当下说明与历史现场记录 |
| **带来源声明的整理稿** | Issue 自身标注为“维护者说明、AI 整理”的内容 | 证明仓库存在该来源声明，并可作为待实现的方向输入；不能独立证明每个扩写命题均获维护者逐项确认，也不能当作维护者逐字原话 |
| **调查推断** | 从事实进行的系统或因果分析 | 必须保留竞争解释，不能伪装成历史原话 |
| **未知** | 仓库和维护者现有说明都不能恢复 | 不补写故事，不用时间顺序冒充思想因果 |

本文坚持以下边界：

- Git 可以证明一段文字何时出现，不能证明维护者何时产生了对应想法。
- GitHub 显示 `spojchil` 创建或合并，不等于能识别操作背后是人直接撰写、Agent 代写还是混合流程。
- `merged`、`accepted`、`normative` 是仓库状态，不自动等于产品所有者逐字确认。
- 代码探针可以证明当前行为，不能证明当时作者为什么写下它。
- 多个 AI 读取相同仓库并得出相同结论，只能提高检索覆盖率，不能成为对维护者意图的独立证据。

本调查使用并行路径寻找证据和反证，但不把“多个审查者同意”当作产品事实。产品意图以维护者直接说明为准；带来源声明的整理稿作为方向输入，并保留其转述与扩写边界；代码和历史只用于确定实际行为及传播过程。

## 3. 精确代码与当前有效语义

### 3.1 当前生产代码

调查基线中，`src/companion/runtime.ts` 的关键部分位于 `#handleChat`：

```ts
const message = interpretPlayerChat(event, {
  companionUsername: snapshot.self.username,
  primaryPlayerUsernames: [this.#primaryPlayer],
  onlinePlayerUsernames: snapshot.trackedPlayers
    .filter(player => player.listed)
    .map(player => player.username),
  conversationActiveWith: this.#primaryPlayer,
})
if (!message?.addressing.addressedToCompanion || !message.sender.isPrimaryPlayer) return
const journalEvent = await this.#journal.append('player.chat.received', {
  sourceEventId: message.sourceEventId,
  sender: message.sender.username,
  text: message.text,
})
```

当前行号约为 `src/companion/runtime.ts:262-274`，目标守卫在第 268 行。`git blame` 仍把守卫、`primaryPlayerUsernames` 和 `conversationActiveWith` 归给 PR #31 的 squash 提交 `ff6cd0c`。

### 3.2 Parser 原本保留了两个独立维度

`src/speech/chat-input.ts` 中，Parser 分别计算：

```text
addressedToCompanion：这句话是否在对同伴说
isPrimaryPlayer：发送者是否属于配置的主要玩家集合
```

明确点名同伴会产生 `explicit_name` 证据；发送者是不是主要玩家是另一字段。也就是说，数据模型能够自然表达：

```text
Bob 不是主要玩家，但 Bob 明确在对 MineIntentBot 说话。
```

PR #31 的 Runtime 才把两轴压成同一准入条件：

```text
进入 Runtime = addressedToCompanion AND isPrimaryPlayer
```

### 3.3 `conversationActiveWith` 让身份条件进一步吞掉寻址条件

Runtime 并没有维护一个真实、可变化的当前对话对象，而是每次都传：

```ts
conversationActiveWith: this.#primaryPlayer
```

Parser 因而永远把主要玩家视为正在与同伴持续对话。对符合基本格式的公屏玩家消息，可以近似化简：

```text
addressed(primaryPlayer) = true
accepted = addressed AND isPrimaryPlayer
因此 accepted ≈ isPrimaryPlayer
```

所以用户的口述简写虽然不是逐字源码，却抓住了当前有效政策：

```ts
if (sender !== primaryPlayer) return
```

### 3.4 只读行为复现

调查使用当前 `interpretPlayerChat` 做了一个不修改仓库的探针。上下文为：

```text
companion = MineIntentBot
primaryPlayer = Alice
online = Alice, Bob, MineIntentBot
conversationActiveWith = Alice
```

结果：

| 发送者 | 文本 | Parser 是否认为指向同伴 | 证据 | 是否主要玩家 | Runtime 是否接纳 |
| --- | --- | ---: | --- | ---: | ---: |
| Bob | `MineIntentBot，你能听见吗？` | 是 | `explicit_name` | 否 | 否 |
| Bob | `大家好` | 否 | `not_addressed` | 否 | 否 |
| Alice | `大家好` | 是 | `ongoing_conversation` | 是 | 是 |

这不是“寻址算法较保守”。第一行已经证明寻址算法正确识别了 Bob 的明确呼叫，丢弃发生在寻址完成之后。

### 3.5 丢弃不是“不回复”，而是“从 AI 世界中删除”

守卫位于 `player.chat.received` Journal 写入之前。因此被排除消息：

- 不产生 `player.chat.received` Journal 事件（Backend chat event 已经到达 Runtime）；
- 不进入 AgentFrame；
- 不触发模型；
- 不进入模型对话历史；
- 不成为记忆证据；
- 不产生“我忽略了谁”的可观测记录；
- 不能由 AI 稍后自行回看。

当前仓库虽然在信息接口类型和架构文档中出现过 `chat_information`，但生产 Provider 集合没有聊天历史实现。被挡住的消息不是“暂不主动通知、但仍可查询”，而是对当前 Agent 永久不可见。

## 4. 两种产品的行为对照

这里的差异不能只写成“支持多人”与“不支持多人”。复杂多人关系是否属于第一版，不是关键分界。真正的分界是：谁拥有身份、注意、历史和关系解释权。

| 维度 | `main@46bcd4d` 的当前实现或明确缺口 | Issue #109 所记录、带来源声明的方向 |
| --- | --- | --- |
| 游戏内身份 | 配置中预先指定一名 `primaryPlayer` | 所有游戏内玩家系统身份同级 |
| 主要关系 | 配置先确定聊天入口的中心玩家；当前没有完整多人关系机制 | 关系由共同经历和 AI 的记忆形成 |
| 谁能唤醒模型 | 实际上几乎只有主要玩家 | 由 AI 管理的关注策略决定 |
| 明确点名 | 非主要玩家点名也被丢弃 | 点名、关注和情境由 AI 判断 |
| 未关注消息 | 不进入 Journal，也无历史工具 | 不主动通知，但保留公屏历史供查询 |
| 关系表示 | 当前生产使用通用 `MemoryRecord` 文本摘要，没有专用关系核心；历史规范和实验曾围绕 primary 扩展结构化关系 | AI 直接维护自然语言关系记忆 |
| 外部管理者 | 部署者必须在配置中选择一个特权游戏用户名；独立的数据管理平面尚未实现 | 游戏外数据管理权与游戏内社会身份分离 |
| 单人与多人 | 单人切片被固化成运行时身份结构 | 同一机制，只有参与者数量不同 |
| 其他玩家的产品角色 | 可见的世界对象、旁观者或环境背景 | 可以被注意、认识、记忆和形成关系的参与者 |

**产品层调查推断：** 当前行为不能只用“多人能力还没做完”概括。它更接近：

> 一个可以部署在多人世界中的私人同伴客户端；一名预设玩家拥有认知入口，其他玩家主要作为环境与观察者存在。

Issue #109 记录的目标产品则更接近：

> 一个生活在共享世界中的社会参与者；AI 自己决定关注谁，并保留对公共世界历史的可恢复访问。

二者的代码可能共享绝大多数模块，但产品主体不同。

## 5. 完整历史重建

### 5.1 2026-07-12 17:29：最早仓库文本已经包含张力

提交 `078f525` 建立最初产品和系统设计。它同时包含两组看似兼容、后来却被不同方式放大的内容。

一组是首版范围：

- 第一版默认单人游玩，或一名主要伙伴与一个 AI 同伴；
- 复杂多人关系、多人控制权、阵营和群体协作不属于首版验收；
- 如何识别主要伙伴、如何处理其他玩家仍是后续细化问题。

另一组是社会行为边界：

- 服务器可以出现其他真人，AI 可以进行基本交流；
- 多人环境不能假定所有聊天都在指挥 AI；
- 社交判断不应被编码成固定阈值、权限表或行为规则；
- 程序只应硬保留停止、真实性和服务器权限等必要边界。

**仓库事实：** 最早文本确实有“主要伙伴”，所以不能说 PR #31 凭空创造了该概念。

**同样是仓库事实：** 最早文本没有授权“其他玩家即使明确呼叫也应从 AI 的认知中消失”。恰恰相反，它保留了基本交流，并把其他玩家关系列为开放问题。

**未知：** 这些最早文本中每句话由谁首次提出、维护者看过哪一段、当时是否已经形成 #109 那样完整的身份观，Git 无法证明。本文只称其为“最早仓库文本”，不称为维护者思想史的逐字记录。

### 5.7 PR #31 将守卫、配置、测试和主要玩家能力打包固化

PR #31 同时让 `MINEINTENT_PRIMARY_PLAYER` 成为必填配置。同批进入 `main` 的实现还包括：

- 模型上下文直接携带主要玩家；
- `follow_player` 无参数跟随配置者；
- 共同活动完成记忆固定写入主要玩家名字；
- 共同活动和原型能力围绕配置玩家组织。

此外，早于 PR #31 的 PR #22 规范已经出现 `relationship_core` 和 `primary_player` audience；PR #31 之后的实验提交 `29052bf` 又实现了 `relationship_core`，但没有进入最终 `main`。两者都不能描述为 PR #31 的同批生产代码。

这些制品表明守卫后来并非孤立存在，而是嵌入了一组相容的中心化前提。它们有的更早、有的同批、有的更晚，不能反过来证明守卫最初为何写入，也不能写成由守卫单向造成。

更重要的是，系统开始缺少反事实数据。非主要玩家消息在入口消失，后续模型、记忆、调试和测试都不会遇到“Bob 明确叫我但我没听到”的失败样本。

### 5.8 2026-07-14：另一条“安静真人”链出现，但不能倒推为本事件起源

Issue #70 和 PR #71 把“较安静、反应较慢的普通玩家”写成长期可信性目标，并把部署者、主要玩家与其他观察者区分开。

**调查推断：** #71 同时使用“主要玩家”和外部观察者，因而与既有 `primaryPlayer` 结构相容；这种组合容易被后续读者组织成“私人同伴 + 旁观盲测”的完整叙事。仓库没有证明两条链之间存在思想因果。

但时间线很清楚：PR #31 比 Issue #70 和 PR #71 更早。因此不能写成：

```text
安静真人目标 → 产生 primaryPlayer 守卫
```

二者是两条不同的漂移链，后来汇合，而不是同一条起源链。

### 5.9 2026-07-23：代码后果已被看见，但没有被识别为根产品问题

`docs/proposals/embodiment-architecture-reflection.md` 明确记录：Parser 已有 addressing，Runtime 却直接丢弃所有非主要玩家消息。

这说明不能说“直到 Issue #109 才有人看见那一行”。它在 #109 之前已经被准确读到。

但现存反思文档把它描述成多人盲测中的可见特征：“完全不回应其他玩家会让它显得不像普通玩家”。该文档记录了**外部观察效果**，没有记录对以下更根本问题的继续追问；这不能证明所有当时审查者都没有想到它们：

```text

为什么 AI 自己没有注意和关系选择权？
为什么未被主动处理的公屏历史会被删除？
```

同一时期，决策登记册 D35 仍写着“如何处理其他玩家”尚待决定，需要确定可见聊天、回应范围、记忆隔离和谁能暂停同伴。

此时出现一个非常关键的矛盾：

```text
产品/架构文档：其他玩家可以交流
决策登记册：其他玩家政策尚未决定
生产代码：十天前已经静默决定全部丢弃
```

也就是说，显式决策仍是开放问题，隐式实现却已经是一套完整政策。

### 5.10 2026-07-23 PR #72：治理把仓库状态变得更清楚，也放大了权威混淆

PR #72 建立文档元数据和治理规则，规定只有 `accepted + normative` 文档可以作为长期约束，并写下“合并的 PR 是接受证据”。

这套政策晚于目标守卫十天，不能把守卫的产生归咎于它。它也确实改善了历史文档、提案和当前状态混用的问题。

但在本项目的实际操作模式下，它产生了新的风险：

```text
Agent 生成文本
→ 文本经同一 GitHub 身份进入 PR
→ 平台仍以同一身份记录创建与合并
→ merged 被解释成 accepted
→ 后续 Agent 把该文本当作产品所有者授权
```

平台无法恢复每次合并的实际操作者、合并前的线下审查或维护者确认范围；上图描述的是可发生的权威混淆机制，不是对每次点击者的断言。

PR #72 自己记录 required approval 数为 0。对单人仓库这是现实选择，但它意味着“经过 PR”只证明变更经过了一个 GitHub 形状，不能证明维护者逐句确认了其中的产品前提。

更具讽刺意味的是，当前 `docs/architecture/companion-runtime.md` 被标为 `accepted / normative / implementation: diverged`，其中仍写着其他玩家可以交流；而代码和 README 运行在主要玩家专属路径上。仓库内部同时存在相互冲突的“权威”。

### 5.11 2026-07-24 至 07-27：实验验收把假设变成前置条件

2026-07-24，D40 实验分支提交 `c5cd238` 新增 `scripts/d40-observer.mjs`。它要求测试身份必须等于 `MINEINTENT_PRIMARY_PLAYER`，否则拒绝运行，并明确提示“同伴只回应主要玩家”。PR #78 于 07-25 只把这项实验前提写入 `main` 的决定记录；脚本后来在实验分支重命名，并到 PR #93 于 07-27 合并时才以当前 `scripts/live-observer.mjs` 进入 `main`。

这个检查在局部上完全合理：既然当前 Runtime 只回应主要玩家，测试身份不匹配就无法执行场景。

但在产品层，它完成了一次反转：

```text
原本应该被验证的产品假设
→ 变成了运行测试必须满足的前置条件
```

在该实验及当前脚本的现场验收中，构造都保证不会出现最关键的反例。测试不是发现“为什么 Bob 不能叫醒同伴”，而是先把测试身份配置成 Alice，再证明 Alice 路径稳定。

PR #93：

| 阶段 | 守卫的实际权力 |

## 6. 为什么说“一行后来成立了另一种产品”

### 6.1 它是一条运行时法律，不是一条普通局部优化

普通优化改变延迟、内存或错误率。此守卫改变的是：

- 谁有资格成为输入主体；
- 谁能触发推理成本；
- 谁的语言能成为共同经历；
- 谁有机会让 AI 形成关系；
- 谁的存在会留下可恢复的历史。

这些问题共同定义产品中的“人是谁”。因此它具有宪法性质，即使代码只有一行。

### 6.2 它处于高扇出的 choke point

该行位于 Backend 和所有上层能力之间：

```text
Minecraft 公屏事件
        ↓
Parser：识别 sender、addressing、primary 标记
        ↓
Runtime 守卫  ← 产品分叉点
        ↓
Journal
        ↓
AgentFrame / 模型
        ↓
工具、说话、episode 记忆、动作
```

只要在这个位置 early-return，后续聊天触发、模型对话历史以及由该聊天产生的说话、动作和记忆路径都无需再写“忽略 Bob”；它们只会接触获准发送者。感知和世界快照仍可能呈现其他玩家，因此这里不是整个系统的单用户锁。

这也是为什么代码量不是衡量产品影响的好指标。高扇出入口的一行，可能比下游数千行工具实现更接近产品定义。

### 6.3 它把描述性字段提升成了授权字段

`isPrimaryPlayer` 在 PR #28 中是消息发送者的描述性标签，并参与特殊安全停止判断。PR #31 把它用于一般准入：

```text
“他是不是主要玩家？”
→ “他的消息有没有资格存在？”
```

这是典型的“描述转授权”。字段名本身没有 `permission`、`admission` 或 `drop`，所以产品变化没有在代码词汇中显形。

### 6.4 它把两个合理判断伪装成同一种 guard

守卫的第一半：

```ts
!message?.addressing.addressedToCompanion
```

处理两件容易被接受的事：Parser 可能返回空；多人公屏并非都对同伴说。

守卫的第二半：

```ts
!message.sender.isPrimaryPlayer
```

则是在制定社会准入政策。

二者被一个 `||`、一个 `return` 和同一行代码捆在一起。视觉上，它们都像“无关或无效输入的普通过滤”。第一个条件的合理性给第二个条件借来了合理性。

### 6.5 它通过负空间定义产品

如果代码写的是：

```ts
grantPermanentConversationPrivilege(primaryPlayer)
```

审查者会立即意识到这是产品决定。

实际代码使用 early-return。它没有创建一个显眼对象，而是让一个主体从后续世界消失。缺失的消息、缺失的关系、缺失的测试和缺失的日志都不会出现在 diff 中。

这是一种“负空间产品设计”：产品不是由新增对象显形，而是由谁永远到不了下游决定。

### 6.6 同批固化与后续延续可能形成强化环

守卫、必填配置和固定发送者测试夹具在 PR #31 同批进入；早期规范文档则独立存在，不能写成守卫的下游。此后 README、现场脚本和重构继续沿用主要玩家前提，可能形成以下强化环：

```text
守卫 + 必填配置 + 单人测试夹具同批固化
→ 非主要玩家在 Runtime 中被丢弃
→ 日志里没有相关失败
→ 模型和记忆从未遇到其他人的对话
→ 后续现场脚本要求测试身份匹配主要玩家
→ README 根据已实现路径描述主要玩家
→ 后续 Agent 读取一致证据
→ 守卫看起来更像早已确认的产品事实
```

这是“多处一致”却不构成独立证明的一种具体机制。后期制品的一致性可能主要是同一入口条件的回声；更早规范中的反向语句仍是独立反证。

## 7. 因果责任边界：哪些是直接后果，哪些不是

为了避免把故事写得过于漂亮，必须按因果强度分类。

### 7.1 守卫的直接后果

| 结果 | 证据强度 | 理由 |
| --- | --- | --- |
| 非主要玩家明确点名也不触发模型 | 直接事实 | Parser 通过、Runtime 守卫失败 |
| 非主要玩家消息不写应用 Journal | 直接事实 | early-return 位于 append 之前 |
| AI 无法用当前工具回看这些消息 | 直接事实 | 没有生产聊天历史 Provider |
| 非主要玩家不能通过聊天触发说话、动作或记忆 | 直接事实 | 所有这些能力都位于模型路径下游 |
| 当前唯一模型入口由主要玩家垄断 | 直接事实 | PR #93 后只有聊天模型路由 |
| 被忽略行为缺少自我观测证据 | 强推断 | 无 Journal、无 history、无 rejection telemetry |

### 7.2 目标代码附近、共同构成产品的假设

这些不是单独由一行 `return` 造成，但与它共同建立了当前行为：

- `MINEINTENT_PRIMARY_PLAYER` 必填；
- Runtime 持有永久 `#primaryPlayer`；
- `primaryPlayerUsernames` 只传一个配置值；
- `conversationActiveWith` 永久等于该值；
- 当前模型只有聊天触发路由；
- README 和运行指南以主要玩家路径描述产品。

最准确的技术说法是：

> early-return 是政策闸门；配置和永久会话上下文让闸门的身份条件退化为全局单用户政策。

### 7.3 更早或平行存在，不能归因于该行的内容

- v0.1 聚焦一名主要伙伴；
- 主要玩家的特殊停止/控制语义；
- PR #22 的主要玩家关系核心；
- PR #25 的主要玩家感知与预算优先；
- 结构化 `MemoryRecord` 和社会关系 schema；
- “安静真人”与行为图灵测试目标；
- 外部管理者和游戏内主要玩家的概念混用。

这些可以与守卫共同塑造另一种产品，但不能写成“那一行导致了它们”。部分内容在它之前存在，部分属于另一条后来汇合的漂移链。

### 7.4 后来已经删除的历史实现

PR #93 删除了 `main` 上的显式 `DecisionContext.primaryPlayer`、硬编码原型 follow skill、活动记忆路径和特殊停止机制。实验分支提交 `29052bf` 曾实现的 `relationship_core` 没有进入 PR #93 的 `main` 祖先，也不能说是由 PR #93 从 `main` 删除。当前记忆实现同样不能简单描述成“每名玩家固定关系字段”。

调查报告必须区分：

```text
历史实现曾经存在
当前生产实现仍然存在
规范文档仍然描述
提案尚未接受
```

否则会把语义传播误报成当前代码全貌。

## 8. 为什么普通代码审查很难把它看成产品假设

### 8.1 它在局部上完全正确

从普通 TypeScript 审查看：

- `message` 可能为空，optional chaining 正确；
- 不指向同伴的公屏消息不应触发模型；
- `isPrimaryPlayer` 是现有类型字段；
- Runtime 本来就有 `primaryPlayer` 配置；
- 单人原型测试全部通过；
- early-return 简短、惯用、没有明显复杂度。

如果审查问题是“这里会不会崩溃”，这一行几乎没有问题。

### 8.2 产品假设没有以产品词汇出现

代码没有写：

```text
其他玩家不是同伴的社会参与者
只有部署者指定的玩家有永久唤醒权
未授权玩家的公开消息应永久删除
```

它只写了布尔条件。审查者必须自行把一行控制流投影成多人服务器中的长期行为，才能看到真正的产品含义。

### 8.3 大 diff 把行为政策降格成胶水细节

PR #31 新增 43 个文件、近 1800 行，目标是完成整个 v0.1 闭环。审查注意力自然会被以下内容吸引：

- 模型密钥和适配器；
- 动作锁、取消和超时；
- 真实 Paper 场景；
- 记忆是否有证据；
- 调试接口是否泄漏；
- 技能是否验证结果。

一行 guard 既没有复杂算法，也没有失败测试。一种合理的机制解释是：审查注意力更容易被上述复杂边界吸引，而这行被归入“把模块接起来所需的普通条件”；仓库不能证明每个审查者当时实际把注意力放在哪里。

PR #93 更大：65 个文件，新增和删除合计超过六千行。它触及守卫所在函数，却把注意力集中在工具协议、缓存、视口、资源仲裁和 scope。守卫作为既有代码，不再拥有“新增行为”的视觉信号。

### 8.4 代码审查通常验证实现是否忠于附近前提，不验证前提是否属于产品

附近类型、配置、文档和测试都说“primaryPlayer”。所以普通审查会问：

```text
代码有没有正确过滤到 primaryPlayer？
```

而真正需要问的是：

```text
为什么“primary”在这里意味着认知准入，而不是控制权限、原型焦点或自然形成的关系？
```

前一个问题有代码答案；后一个问题需要产品所有者。

### 8.5 看见代码不等于看见假设

2026-07-23 的架构反思已经逐字指出“Runtime 丢弃所有非主要玩家”。这说明失败不是“没人打开文件”。

现存反思文档使用“像不像普通真人”的框架，把同一事实记录成盲测特征，没有继续写出身份主权分析。这证明文档留下了什么解释，不证明所有参与者当时只想到这一种解释。

这正对应用户的直觉：即使看见

```ts
if (sender !== primaryPlayer) return
```

也可能只检查：

- sender 是否可能为空；
- 比较是否大小写敏感；
- primaryPlayer 是否已配置；
- return 是否避免无关调用。

产品假设不在语法里；它来自对反事实世界的比较。

## 9. 为什么测试全绿仍然发现不了

### 9.1 测试输入已经接受了待验证前提

当前 Runtime 测试的发送者无法参数化，永远是 Alice；Runtime 的主要玩家也永远是 Alice。

因此测试空间在进入断言前已经满足：

```text
sender === primaryPlayer
```

目标守卫在每个测试中都为真分支，无法被观察。

### 9.2 现场验收主动消除了反例

现场观察脚本在 tester 与 primary 不一致时拒绝运行。这保证实验稳定，却也保证不会测试其他玩家是否能够被听见。

这是一种常见的测试固化：

```text
实现限制
→ 测试环境要求
→ 验收前置条件
→ “所有验收通过”
```

### 9.3 负分支没有 telemetry

如果系统至少记录：

```text
chat.rejected: sender=Bob, reason=non_primary
```

那么日志、调试状态和现场实验会积累异常信号。当前 early-return 什么也不写。每一次被拒绝都同时销毁了发现它的证据。

### 9.4 测试验证机制，不具备产品 oracle

测试可以证明：

- 同一发送者的消息按顺序处理；
- scope 改变会取消旧 run；
- 工具调用不会越过资源边界；
- Journal 写入与模型调用协调正确。

测试无法从代码内部推导：

- 所有游戏内玩家是否应同级；
- 谁应拥有唤醒权；
- 未关注消息应删除还是保留；
- 主要伙伴应配置还是由关系自然形成。

没有人类确认的行为契约时，“测试通过”只说明代码忠实实现了当前假设。

## 10. 为什么多个 AI 审查也不构成独立复核

### 10.1 它们共享同一被污染前提

后续 Agent 会同时读到：

- `MINEINTENT_PRIMARY_PLAYER` 必填；
- Runtime 只接受主要玩家；
- 测试只发主要玩家消息；
- README 说主要玩家消息进入模型；
- 运行指南要求填写主要玩家；
- 现场脚本要求 tester 等于主要玩家；
- accepted 文档中存在 `primaryPlayerId` 和关系核心。

这些不是七个独立来源，而可能是同一个早期假设的七次投影。

### 10.2 检索越认真，错误前提可能越可信

一个认真审查的 Agent 会搜更多文件。结果是它看到更多相互一致的 `primaryPlayer` 证据，从而提高对前提的信心。

如果它没有一份独立、由维护者确认的最小产品基线，那么“仓库一致性”会被误当成“产品正确性”。

### 10.3 Agent 同时扮演提案人、实现者、测试者、记录者和审查者

在本项目可见流程中，同一类 Agent 可以连续完成：

```text
提出范围解释
→ 写设计
→ 写代码
→ 写测试
→ 写 PR 正文
→ 触发合并
→ 在后续 Issue 中引用这些材料
```

每一步都可能内部一致，却没有产生新的产品权威来源。

### 10.4 AI 并非不能审查，而是不同问题需要不同 oracle

仓库其他事件表明 AI 可以有效发现：

- 局部机制矛盾；
- 生命周期和 scope 错误；
- 可计算的非对称后果；
- 类型、协议和状态机不变量；
- 通过实验、变异或服务端真值产生的反例。

但“什么算同伴”“谁是社会主体”“像真人是不是目的”没有代码内 oracle。Agent 只能读取现有目标文本；一旦目标文本本身被污染，审查者会忠实地继续执行错误目标。

## 12. 维护者在仓库中的“存在”：有产品权威，却没有可靠作者身份

用户在本次对话中明确说明：

- 没有亲自写一行代码；
- 没有亲自写一行 PR；
- 没有亲自写一行 Issue。

然而 Git 和 GitHub 的主要可见身份都是 `spojchil`。这形成了一个重要的认识论错位：

```text
平台 actor = spojchil
不等于
文本物理作者 = 维护者本人
也不等于
产品判断已被维护者逐句确认
```

部分较晚提交自愿带有 Claude 或 Codex 的 `Co-authored-by` 标记，部分 PR 正文也声明由 Claude Code 生成；PR #31 等较早关键提交没有这些标记。没有标记不能反推成人类写作，因为标记从未被系统强制。

维护者的真实存在主要体现在另一层：

- 指出项目想成为什么；
- 在架构讨论中推翻错误抽象；
- 识别“像真人”与“同伴”不是同义；
- 在 Issue #109 中拆分身份、注意、历史、关系和外部管理权；
- 发现 Agent 已经围绕错误前提建立了自洽系统。

问题不是维护者“不存在”，而是现有仓库把两类活动压成同一账号轨迹：

```text
Agent 生产制品
维护者作方向判断
```

GitHub 能记录谁的凭据执行了操作，却不能自动记录一句具体产品前提是 Agent 提议、维护者原话、共同推导，还是尚未被确认。

这也解释了为什么“专门注册一个 Agent GitHub 账号”不是唯一解，甚至不是充分解。账号分离能改善操作来源，却仍不能回答：

- 维护者确认了哪一句准确文本？
- 确认的是方向、技术路线还是验收代理？
- Agent 在转述时增加了哪些推断？
- 一个 merged PR 中哪些产品假设仍未被人看见？

真正缺失的是**命题级来源和确认状态**，不是单纯的账号标签。

## 13. 竞争解释与反证

一个可靠调查必须主动保留让主叙事不那么漂亮的事实。

### 13.1 竞争解释 A：这只是合理的 v0.1 范围捷径

这是最强替代解释。Issue #17 只要求一个玩家与一个 AI 的木材闭环；限制模型只响应配置玩家，可以减少噪声、成本和测试复杂度。

**可以支持它的事实：**

- 最早产品边界明确聚焦一名主要伙伴；
- Issue #13 / PR #21 都以单伙伴场景为目标；
- PR #31 是纵向原型，不是完整多人发布；
- 没有证据表明作者当时想永久定义社会身份。

**不能由此推出的结论：**

- 范围捷径可以不声明；
- 非主要玩家消息应在 Journal 前永久删除；
- 测试范围可以自动成为生产身份模型；
- 后续重构可以继续把它当作默认产品事实。

因此最公允的判断是：原型收窄是与现有证据相容、也很直接的一种解释，但当前无法为它赋予可靠概率；无论初始动机如何，该行为后来获得了远超原型范围的产品权力。

### 13.2 竞争解释 B：主要玩家特殊控制权自然要求过滤

PR #21 确实只给主要玩家确定性快速停止权。

但 PR #21 同时明确说其他玩家可以交流，原始聊天都保留。PR #28 也只限制 `controlIntent`，不删除消息。因此“没有特殊控制权”不能解释“一般聊天完全不可见”。

### 13.3 竞争解释 C：多人关系本来就不属于第一版

这是真的，但“复杂关系不验收”与“基本聊天删除”不是同一个命题。让 Bob 明确点名时被模型看见，不要求完整社会图、阵营、关系状态机或群体协作。

守卫不是“未实现复杂多人”，而是对最基础的主体可达性做了确定性否定。

### 13.4 竞争解释 D：运营安全、成本或提示攻击边界

只允许配置玩家触发付费模型，也可能用于防止陌生玩家刷调用、提示攻击或恶意操控。这些都是与守卫形状相容的初始动机，但 PR #31 没有记录其中任何一个，因此必须保持未知。

即使该解释成立，它也只能解释“为什么不让每个人主动触发模型”，不能解释“为什么消息必须在 `player.chat.received` 之前消失、且以后无法回看”。成本控制、主动通知和历史保留仍是三个不同命题。

### 13.5 竞争解释 E：不完整实现或普通缺陷

PR #21 的规范允许其他玩家交流，而 PR #31 的 v0.1 只实现了主要玩家子集。最简单的历史解释也可能只是功能没有做完或普通遗漏，而不是任何人有意识地设计了另一套社会产品。

必须保留这个区别：

```text
行为上已经构成另一种产品
≠
当时有人有意识地设计了另一种产品
```

本文调查的是前者。现有证据不足以宣布后者。

### 13.6 反证：系统并没有从底层完全单用户化

当前系统仍保留多人的若干能力：

- Backend 接收任意玩家的公屏聊天事件；
- Snapshot 和 viewport 可以包含其他玩家名字；
- AgentFrame 的 player 字段接受普通 username；
- `say` 发送到公共聊天；
- Parser 可以表示 non-primary addressed message。

所以不能写成“整个系统只认识一个玩家”。更精确的结论是：

> 单用户锁位于进入 deliberation 的入向 choke point；世界模型和输出通道仍可以呈现其他玩家。

这也是为什么问题能隐藏得如此好：大部分类型看起来支持多人，只有一处组合逻辑取消了这种能力。

### 13.7 反证：问题在 #109 前已经被发现

架构反思和 D35 已经指出现象，所以不能宣称所有 Agent 都完全没看见。

现存反思文档把现象记录成盲测特征，D35 则保留为待定多人功能；它们没有留下“宿主预先分配社会主权”的根产品分析。这里评价的是仓库记录，不是对所有当时参与者思想的推断。

### 13.8 反证：不是所有下游内容仍在当前生产代码中

PR #93 已删除一些主要玩家专属内部结构。若把历史设计全部描述成当前实现，会夸大偏离范围并削弱报告可信度。

当前确定仍存在的核心是：必填配置、永久 Runtime 字段、聊天 Parser 上下文、early-return、单一模型入口、主要玩家测试夹具、现场验收前置条件和读者文档。

这些未知不妨碍确认当前代码与 Issue #109 所记录、带来源声明的方向冲突，但它们阻止本文制造一条过度确定的思想史。

## 15. 为什么删掉这一行仍然不是修复

如果只删除 `!message.sender.isPrimaryPlayer`，当前系统会发生：

- 所有被 Parser 认为 addressed 的玩家消息都可以触发模型；
- Bob 的明确点名开始进入 Journal 和模型；
- 但关注策略仍不由 AI 管理；
- 未关注公屏历史仍没有生产工具；
- `MINEINTENT_PRIMARY_PLAYER` 和永久会话对象仍存在；
- 主要玩家的普通公屏消息仍被自动视为持续对话；
- 当前实现尚未建立 #109 所述的独立外部数据管理平面；
- 关系和记忆迁移仍未完成。

更糟的是，简单放开可能让多人服务器中每个显式点名都直接触发模型，仍未解决成本和注意噪声。

因此，这一行是**最小问题见证**和**否决点**，不是完整因果，也不是完整修复面。

Issue #109 要求替换的是一组机制：

```text
公屏消息先成为可恢复历史
        ↓
AI 管理关注列表，决定哪些发送者会主动通知
        ↓
被唤醒后，AI 自己决定是否回应、怎样回应、是否形成关系
        ↓
关系解释写入 AI 自己可编辑的自然语言记忆
        ↓
外部管理者可以管理数据，但不因此获得游戏内社会特权
```

修复的关键不是把“主要玩家”替换成“所有玩家”，而是把以下维度重新拆开：

- 身份平等；
- 主动通知；
- 历史可见性；
- 对话寻址；
- 控制与安全；
- 关系理解；
- 外部数据管理。

## 16. 对当前仓库状态的判断

截至 `main@46bcd4d`：

### 已经明确的事实

- 当前唯一模型触发受该身份约束；

- README 和指南仍把主要玩家当作正常运行主体；
- accepted Runtime 设计反而保留其他玩家交流，仓库内部存在冲突；
- Issue #109 已以“维护者说明、AI 整理”的来源标记记录方向纠正，但尚未实现到 `main`。

### 因此不能声称的状态

- “多人关系只是未来功能，当前行为符合既定产品”——不成立，因为当前行为连早期允许的基本交流也删除。
- “所有测试通过，所以 v0.1 产品闭环有效”——只能说主要玩家技术路径通过。
- “已经有 100 多个 Issue/PR，所以产品决定足够充分”——编号和制品数量不能替代产品权威。
- “删一行即可恢复正确产品”——不成立，缺少注意和历史机制。
- “当前没有可用发布只需继续堆功能”——至少还存在一项独立的根身份模型冲突，不能只按功能数量处理。

本事件说明，高工程吞吐并不保证产品前提同步收敛。它可能是当前仍不可用、不可发版的原因之一；项目只有两周、能力尚未完成等同样是明显的竞争解释，现有证据不能确定各因素的相对权重。

## 17. 流程层修复建议

本节不替代 Issue #109 的产品和实现迁移，只针对这类“一行代码承载隐藏产品宪法”的流程问题。

### 17.1 不要求维护者审查千行 diff，改为审查行为反事实

每个会改变主体、权限、注意、记忆或可见性的 PR，在写代码前提交一张很短的行为表：

| 主体/场景 | 改动前 | 改动后 | 是否由维护者确认 |
| --- | --- | --- | --- |
| Alice 普通公屏发言 | ？ | 唤醒模型 | 待确认 |
| Bob 明确点名同伴 | ？ | 永久丢弃 | 待确认 |
| Bob 未被关注的公屏消息 | ？ | 是否保留历史 | 待确认 |
| 外部管理者不进游戏 | ？ | 有无数据管理权 | 待确认 |

维护者不需要读 TypeScript，也能直接判断产品后果。

### 17.2 单独列出“新增产品假设”

PR 正文必须有一个短区块：

```text
新增产品假设：
- 只有配置玩家能触发模型。
- 非配置玩家消息不保留。

明确不决定：
- 多人关系模型。
- 外部管理者与玩家身份关系。

可推翻条件：
- 维护者要求所有游戏内玩家身份同级。
```

若 PR #31 当时出现这三行，目标守卫会从“胶水代码”变成可被维护者判断的产品问题。

### 17.3 命题级 provenance，而不是只标整篇文档

建议每条根产品判断标记：

- `maintainer-confirmed`：维护者确认了准确命题；
- `agent-proposed`：Agent 的候选解释；
- `joint`：共同形成并确认；
- `unresolved`：代码需要暂时选择，但产品尚未决定。

不要用文首一句“来源：维护者确认”覆盖后文所有 AI 推断。Issue #108 初版已经证明这种文档级来源粒度不足。

### 17.4 `merged` 与“产品接受”分层

合并可以表示：

- 代码进入 `main`；
- 实验可供使用；
- 机械重构完成；
- 临时原型路径可运行。

只有带准确产品命题、并获得维护者明确确认的记录，才能表示价值判断被接受。

不需要另注册 Agent 账号才能做到这一点。账号分离是可选的操作审计增强；核心是把确认对象从“整个 PR”缩小到“几条产品命题”。

### 17.5 让拒绝路径可观测

任何会删除输入主体的 guard 至少应产生有界、隐私安全的 telemetry：

```text
收到一条玩家消息
是否保存
是否主动通知
未通知原因
是否可由历史工具恢复
```

这样测试和现场日志能看见被排除的世界，而不是让 early-return 同时销毁错误证据。

### 17.6 测试必须包含角色交换和反事实主体

对所有身份判断，最低测试矩阵应包含：

- 主要玩家明确点名；
- 主要玩家对别人说话；
- 非主要玩家明确点名；
- 非主要玩家普通公屏；
- 关注与不关注；
- 消息不唤醒但仍可从历史查询；
- 外部管理者不是任何在线玩家。

尤其不能让 FakeBackend 把 sender 写死，否则测试框架本身就在隐藏产品轴。

### 17.7 审查 AI 使用独立的人类确认基线

审查 Agent 不应仅从代码、README、accepted 文档和旧 PR 相互证明。它应先获得一份很短、只含维护者确认内容的产品内核，并把仓库其他材料视为待核实现。

对本事件，这份内核至少需要回答：

- 是否预设主要玩家？
- 谁能主动唤醒 AI？
- 未通知消息是否仍存在？
- 关系由谁解释和存储？
- 外部管理者与游戏内玩家如何分离？

没有这些答案时，审查 Agent 可以评价代码质量，但不应宣布产品方向正确。

### 17.8 大型机械重构不得静默改变根触发集合

PR #93 删除启动和动作结果模型路线，使既有守卫升级为唯一认知入口。以后任何涉及模型触发集合的重构，都应附一张触发前后表：

```text
startup：有 → 无
player chat：有 → 有
non-primary addressed chat：无 → 无
world/damage event：间接有 → 只缓存，不能单独唤醒
action result：有 → 无
```

这样“没改守卫，但守卫权力变大”的变化才能被看见。

## 18. 调查发现清单

### F1 — 高严重度：控制身份被提升为认知准入身份

- **性质：** 仓库行为事实 + 调查分层。
- **证据：** PR #21、PR #28 与 PR #31 的行为差异。
- **影响：** 非主要玩家失去对话可达性，而不只是特殊控制权。

### F2 — 高严重度：拒绝发生在持久记录之前

- **性质：** 当前代码事实。
- **证据：** `src/companion/runtime.ts` 中守卫位于 `player.chat.received` append 前。
- **影响：** 被拒消息及拒绝行为都不留下 Agent 可见证据。

### F3 — 高严重度：PR #93 使主要玩家获得当前唯一唤醒权

- **性质：** 当前代码事实与历史对比。
- **证据：** PR #93 删除其他模型触发，保留守卫。
- **影响：** 身份过滤从聊天策略变成心智启动边界。

### F4 — 高严重度：当前实现与 Issue #109 记录的方向冲突

- **性质：** 当前代码事实 + 带“维护者说明、AI 整理”来源标记的方向记录。
- **证据：** Runtime/config 与 Issue #109。
- **影响：** `main` 在身份、注意和历史可见性上实现了另一套产品行为；当前生产关系机制尚不完整，不能把所有历史关系设计都算作现行实现。

### F5 — 中高严重度：测试和现场验收结构性排除反例

- **性质：** 测试代码事实。
- **证据：** 固定 Alice/Alex sender；observer 强制 tester 等于 primary。
- **影响：** 全绿无法检验核心产品假设。

### F6 — 中高严重度：显式文档状态与隐式实现政策矛盾

- **性质：** 仓库事实。
- **证据：** accepted Runtime 文档允许其他玩家交流；D35 仍开放；生产代码全部丢弃。
- **影响：** 后续 Agent 可任选一个锚点组织出不同但自洽的结论。

### F7 — 中高严重度：同源制品被误当成独立确认

- **性质：** 流程推断，受 #108 实例支持。
- **证据：** 配置、代码、测试、README、脚本和 accepted 文档共享同一 `primaryPlayer` 前提。
- **影响：** 检索越全面，错误前提可能越显得可靠。

### F8 — 中等严重度：GitHub actor 无法表达真实文本来源

- **性质：** 维护者说明 + 元数据事实。
- **证据：** 用户声明未写代码/PR/Issue；平台主要显示同一账号。
- **影响：** 不能从 author/merge 记录推导产品所有者逐字授权。

### F9 — 限定：目标行不是全部起因，也不是完整修复点

- **性质：** 反证结论。
- **证据：** primary 概念和感知/上下文优先早于 PR #31；#109 需要新的注意与历史机制。
- **影响：** 修复不能停在删除一个条件，也不能把全部历史偏离归咎于一行。

## 21. 最终结论

这次事件最值得保留的，不是“AI 会写错一行代码”这个普通结论。真正的问题更细，也更难：

1. 最早仓库文本把 v0.1 明确写成单主要伙伴场景；
2. 随后的仓库制品把 `primaryPlayer` 写入身份、上下文和感知中心；这些制品是否由首条范围语句推导，现已无法恢复；
3. Parser 仍区分寻址与特殊控制权；
4. PR #31 的守卫在行为上把二者压成一般聊天准入；
5. 该行为没有在可见 Issue、PR 正文、评论或测试中以产品命题显式记录；
6. early-return 让被拒消息在应用 Journal 前消失；
7. 守卫、配置和测试同批固化，后续脚本、README 与重构继续维持这一前提；
8. PR #93 删除其他模型触发后，该守卫成为当前唯一心智入口的身份边界；
9. #109 之前的现有反思文档记录了“丢弃其他玩家”，但只留下了盲测特征这一解释；
10. #109 首次在仓库中完整记录了带维护者来源声明的身份、注意、历史、关系和管理权分层。

所以，“微小的产品假设隐藏在大型 diff 中”并不只是说某个产品句子没有写进 `PRODUCT_DESIGN.md`。更危险的情况是：

> 产品假设根本不像一句产品话。它可能只是一个正确类型、正确空值处理、正确通过测试的 early-return；只有把被它排除的主体、未来触发路径和下游历史一起投影出来，才能看见它实际上在决定产品中的谁有资格存在。

维护者不应被要求从上千行 diff 中靠直觉发现这种宪法性代码。流程应在实现前把它翻译成可判断的行为命题：

```text
Bob 明确叫 AI 时，AI 能不能听见？
如果不主动通知，这句话以后还存在吗？
谁决定关注 Bob？
谁有权把 Alice 设成永久中心？
```

只要这些问题被单独摆到维护者面前，那一行代码就不再隐蔽。真正缺少的不是更多 Agent、更多 Issue、更多 PR 或更多测试，而是一条把代码中的隐含社会政策提前还原成产品语言的审查通道。
