# B6 Participant Runtime 交付日志

## 范围与当前状态

B6 在 `crates/middle/src/participant/` 提供可由 app 组装的 Participant runtime；没有修改 contracts、backend、Cargo 根文件、supplies/vendor 或其他日志。runtime 的 backend 接线命名为 `start_worker`：app 负责按既有 OperationControl 启停 backend，runtime 负责订阅、事件 admission、worker、模型 run 与自身收束；这避免把“只 subscribe”的 API 误称为 backend 全生命周期 owner。

本日志只记录已经有代码或测试证据的内容。`ConnectionClosed` 的可重连语义、closed-scope tombstone、attempt 身份、UUID/SHA-256/base36 RunId、真实 Concrete registry 组合和 blocked-subscribe 迟到 `Err` 回归均已进入当前实现；最终全量门禁和最后一次 mutation 在本日志最后更新。

## 设计与线性化点

- `ParticipantRuntimeConfig` 显式注入 backend、`ParticipantAgentPort`、truthful `ParticipantFrameSource`、memory、journal、speech、debug、clock、prompt、deadline 和 wake registry；`ParticipantRuntime::try_new` 校验 namespace 最终 RunId 长度。
- `ParticipantRuntime::start_worker` 在 `admission_serial` 下发布 Running、接管唯一 receiver、发布 worker，再调用同步 backend `subscribe`。`stop` 不等待 subscribe 返回：同步 stop admission 先取消 generation/active run、cancel remaining speech、release body，并在 worker settle 后处理迟到 handle；迟到 `Ok` 退订，迟到 `Err` 返回结构化失败且不回退 Stopped。`request_stop` 保留同步取消/释放语义。
- `admission_serial` 是 lifecycle、scope、generation、pending facts、wake admission 和 stop request 的同步 FIFO 线性化点；`cleanup_serial` 串行化 cleanup。worker 只按 `WorkItem` FIFO 处理，journal append 完成后再次检查 generation/scope，才允许 frame/memory/model。
- active run 在 runner 越过 start gate 前发布 generation、cancellation 和 gate；generation/lifecycle 使用带状态的 watch 信号，避免检查与注册通知之间的 lost wake。普通事件/排队聊天不执行 cleanup；只有 scope invalidation、terminal、stop 或 handler fault 执行 cleanup。
- `stop` 由 async owner 串行化：所有 caller 等同一 completion 屏障；先等待 cleanup，再给 worker 有界 settle 机会，超限才 abort+join，最终只发布一次 Stopped 资源终态。backend terminal/listener fault 由 worker 收束 subscription；callback 不同步注销自己。
- ParticipantScope 包含 process session、connection epoch、world、dimension。retired process identity 保存非敏感 digest 且 runtime 生命周期内不 eviction；scope 变化清空旧 pending facts、health baseline、sound/伤害事实并使旧 work 失效。
- backend v2 `ConnectionClosed` 不是无条件 Participant terminal：同步 cleanup 后保留 closed scope/high-water 与 closed attempt tombstone，Participant 继续 Running/subscribed；同 process 只有严格更高 epoch 且不同 attempt 的 `ConnectionRequested` 才可重开。wrong-attempt reconnect/terminal、同 epoch 新 attempt、较高 epoch 复用旧 attempt 和 close 后旧 chat 均在 admission 前拒绝。匹配 attempt 的 Faulted/Stopped 才最终 teardown；显式 `ParticipantInternalEvent::Closed` 仍为 terminal。

## 公开 seam

公开组装/观察类型包括 `ParticipantRuntime`、`ParticipantRuntimeConfig`、`ParticipantScope`、`ParticipantEvent`/`ParticipantInternalEvent`、`ParticipantFrameSource`、`ParticipantMemorySource`、`ParticipantSpeechControl`/speech port、`ParticipantClock`、`ParticipantAgentPort`/`ParticipantAgentFactory`、`ParticipantAgentAssembly`、`ParticipantRegistryBound`、`WakeRegistry`/`WakeRule`、`ParticipantFailure`/failure source 和 lifecycle/admission/error 类型。内部 `WorkItem`、Admission 分支、cleanup/failure helper 保持私有。

opening-frame source 是显式端口，不假设 A7 已经有 light/armor 快照：缺 light 返回结构化 `MissingLight`；armor 是原版 0..20，0 在 v5 缺键，非零才写入。后续 app/A7 需要将真实 pose/status/hotbar/light/chat/event 输入接入该端口；B6 不声称已完成 A7 wiring。

agent 组合只接受 factory/runner 自身的 registry binding：生产 `ConcreteAgentRunner<..., RegistryToolDispatcher, ...>` 的 `tool_registry()` 与 Participant factory 的 `Arc<ToolCapabilityRegistry>` 做 identity 校验，definitions 由同一 registry 产生，per-wake 绑定 scope 与 trigger event id；没有 HTTP agent/tool bridge，也没有第二份 registry。
