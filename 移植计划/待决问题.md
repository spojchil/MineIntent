## 二、产品目标与 TS oracle 冲突处

### DELTA-01｜长期记忆目标与当前结构化文件怎样过渡

**证据。** 产品要求每个 AI 只有一份直接提供给模型的长期记忆文本，AI 可直接读写，且不强制记录类型或固定字段（M01-M08，`materials/mineintent-main/产品.md:110-126`）。TS 当前却把 `memories.json` 定义为带 kind、keywords、evidence、worldId 的记录数组，只读取一次并以整份 JSON 重写（`materials/mineintent-main/src/memory/memory-store.ts:7-14`、`materials/mineintent-main/src/memory/memory-store.ts:24-32`、`materials/mineintent-main/src/memory/memory-store.ts:36-75`）；运行时每次只检索最多五条摘要（`materials/mineintent-main/src/participant/runtime.ts:266-298`）。

**选项。**

1. Rust 移植直接落到产品定义的单文本存储，并为旧 `memory-file.v1` 提供一次性导入。
2. 先建立兼容层：读取旧结构并转换为唯一规范文本，旧格式只读、所有新写入走新格式。
3. 暂停记忆子系统的落地，先由维护者回答 Q12 以及文本编辑/冲突语义，再开始该模块。

**影响。** 选 1 或 2 都需要维护者明确旧记录到文本的确定性映射、备份/回滚和 oracle 测试如何改版；选 3 会阻塞 `remember`、opening context 和完整运行时集成。不得把永久照搬结构化多记录作为默认答案，因为 G06a 不允许实现偏差反向修改产品（`materials/mineintent-main/产品.md:21`）。

### DELTA-02｜当前单一提示词与模型专用提示词的迁移阶段

**证据。** TS/Python 只有一个 `system_prompt()`，且把行为约束与工具结果约定写在同一字符串中（`materials/mineintent-main/agent-service/prompt.py:37-49`）；产品把基本背景与长期记忆分开，并允许按供应商、模型和版本维护提示词（S04-S07，`materials/mineintent-main/产品.md:101-107`）。

**选项。** 保持现有共同提示词作为第一版 oracle、只先增加显式版本键；或在移植时就建立共同核心加模型覆盖层；或等待 Q01/Q07 后再改提示词组织。

**影响。** 决定配置键、Agent Service 请求是否携带 prompt profile、Python 测试是否只保持现状，以及何时需要多模型快照测试。

### DELTA-03｜聊天唤醒、全局公屏历史与关注机制的落点

**证据。** 当前寻址证据只有点名、进行中对话和唯一在场三类（`materials/mineintent-main/src/speech/chat-input.ts:8-23`），当前装配只对“被寻址”消息排队决策（`materials/mineintent-main/src/participant/runtime.ts:235-263`）。产品则规定公屏是全局信息、关注只决定主动唤醒而不限制历史查询，并要求保存范围内全部公屏可查（W08-W08c，`materials/mineintent-main/产品.md:131-137`）。

**选项。**

1. 独立实现“所有公屏入历史”与“哪些消息唤醒”两条管线，现有寻址规则只作为首版唤醒策略。
2. 先实现完整历史，再由明确的关注策略接口取代当前寻址入口。
3. 在 Q14 未答前使用可配置、版本化保留策略，但不能少收当前在线期间已进入正常输入范围的消息。

**影响。** 涉及聊天事件 DTO、持久化、查询工具、run 触发与对称性测试；不能让“未唤醒”变成“不可查询”。

### DELTA-04｜正常玩家能力范围如何转成移植后的里程碑

**证据。** P04 要求 AI 为参与共同经历具备正常玩家能力，W09 要求每个视野/身体决定有理由和记录（`materials/mineintent-main/产品.md:26-34`、`materials/mineintent-main/产品.md:138-140`）。当前模型工具只有相对看、短按移动、视口、说话和结构化记忆，且明确没有挖掘、放置、交互、战斗、GUI、制作或装备（`materials/mineintent-main/docs/architecture.md:112-126`）。backend-rs 的既定非目标也排除了容器、制作、挖掘等完整客户端能力（`materials/backend-rs/任务书.md:60-66`）。

**选项。** 把本次中间层移植严格定义为“等价迁移，能力扩展另立路线”；或在迁移里程碑后追加已逐项裁定的身体能力；或先请维护者澄清 P04 的完整性含义再排扩展顺序。

**影响。** 决定本次完成门槛是否只要求 TS oracle 等价，以及 backend-rs 是否必须先扩展；不改变 P04 本身。

## 三、Rust 后端与中间层的接缝

### SEAM-01｜代码与故障边界：链接 crate 还是管理子进程

**证据。** backend-rs 既有进程内 `RuntimeHandle`，直接提供 snapshot、subscribe、observation source 和动作方法（`materials/backend-rs/src/runtime.rs:356-455`），也有 stdin 命令/stdout JSONL 的可执行程序（`materials/backend-rs/src/main.rs:5-38`、`materials/backend-rs/README.md:5-20`）。只有进程内观察源目前提供实体、方块与视口读取（`materials/backend-rs/src/runtime.rs:501-585`）。

**选项。**

1. 将 backend-rs 作为 workspace crate 直接链接，中间层持有 `RuntimeHandle`。
2. 保持独立子进程，扩展命令协议以覆盖查询、响应和取消。
3. 混合：生产链接 crate，独立可执行文件只作验收/诊断入口。

**影响。** 选 1/3 可直接复用观察源但绑定依赖版本、共享 Tokio/故障域；选 2 保持进程隔离，但必须先补齐请求—响应、背压、重启恢复和大视口传输，且子进程退出不能与 Minecraft 掉线混为一类。

### SEAM-02｜`MinecraftBackendApi` 的 Rust 接口由谁拥有、怎样冻结

**证据。** TS 接口把 start/stop/state/snapshot/subscribe/observationSource/motor/sendChat 放在一个对象上（`materials/mineintent-main/src/minecraft/contracts.ts:238-285`）；Rust 将句柄、观察源和命令枚举分开（`materials/backend-rs/src/runtime.rs:356-455`、`materials/backend-rs/src/runtime.rs:501-585`、`materials/backend-rs/src/protocol.rs:89-124`）。

**选项。** 在中间层定义 trait、backend-rs 实现；在 backend-rs 定义公共 trait/类型、中间层直接依赖；或抽出仅含 DTO/trait 的第三个 contract crate。

**影响。** 决定依赖方向、fake backend 测试落点、协议类型是否与游戏实现解耦，以及两个代理并行时谁能改公共契约。

### SEAM-03｜命令“已入队”、客户端执行与服务端结果怎样关联

**证据。** Rust `send_command()` 校验后只入队并返回 `Ok(())`（`materials/backend-rs/src/runtime.rs:389-398`），动作命令携带 id/issuedAt（`materials/backend-rs/src/protocol.rs:224-233`），处理器在后续 tick 执行队列（`materials/backend-rs/src/runtime.rs:977-990`）。产品要求动作通过实际游戏过程发生并按实际结果判定成功/失败（W03，`materials/mineintent-main/产品.md:54-60`）。

**选项。** 为每个 command id 发 accepted/dispatched/observed/failed 事件；进程内返回可等待的 completion handle；或由中间层用前后快照测量、同时把“无可归因的结果”明确返回。

**影响。** 决定 `look_relative`/`move_input` 工具何时完成、超时与取消如何报告，以及 `observationAfter` 能否继续只表达时间相邻而不声称因果。

### SEAM-04｜启动、停止、重连与重生策略由哪一层控制

**证据。** TS 配置包含四段连接超时和带倍率、抖动、稳定重置的重连策略（`materials/mineintent-main/src/minecraft/contracts.ts:11-24`），Rust `RunConfig` 只有运行时长和固定 reconnect delay（`materials/backend-rs/src/runtime.rs:45-73`）。Rust 明确将重生保留为上层显式命令（`materials/backend-rs/src/runtime.rs:443-455`）。

**选项。** 所有生命周期策略放 backend-rs、中间层只订阅；backend-rs 只报告事实而由中间层调度重连/重生；或拆分为“传输级重连在后端、产品级重生/停止在中间层”。

**影响。** 决定配置归属、状态机唯一真源、重连退避的 oracle 测试迁往何处，以及 Q04 的安全控制最终接到哪一层。

### SEAM-05｜如何把取消传播到正在执行的后端动作

**证据。** TS motor 的 look/move 接受 `AbortSignal`，runtime 在 scope 变化时同步 abort、失效租约、停止说话并 releaseAll（`materials/mineintent-main/src/minecraft/contracts.ts:260-274`、`materials/mineintent-main/src/participant/runtime.ts:324-374`）。Rust wire 命令只有 move/releaseAll 等，没有通用 cancel command（`materials/backend-rs/src/protocol.rs:98-124`）。

**选项。** 进程内使用 cancellation token；wire 增加按 command/action id 取消；或规定所有身体取消归一为带 generation 的 `release_all` 并由结果事件确认。

**影响。** 决定掉线残句、移动释放、一条 tool call 一次性以及 stale command 是否可能在新 epoch 执行；相关断言语义必须逐条保留。

### SEAM-06｜事实来源如何进入中间层与模型可见结果

**证据。** Rust 事件新增 commanded/client_predicted/server_observed 来源，snapshot 来源另由句柄查询（`materials/backend-rs/src/protocol.rs:18-25`、`materials/backend-rs/src/protocol.rs:44-60`、`materials/backend-rs/src/runtime.rs:367-375`）；TS `BackendEventEnvelope` 与 snapshot 没有该字段（`materials/mineintent-main/src/minecraft/contracts.ts:118-130`、`materials/mineintent-main/src/minecraft/contracts.ts:225-236`）。产品要求错误世界状态必须修复，且运行时不得把准备执行说成已经完成（W04c、W07a，`materials/mineintent-main/产品.md:57-62`、`materials/mineintent-main/产品.md:131-134`）。

**选项。** 给每个模型可见字段保留来源；只允许 server_observed 进入事实字段、把 predicted 放独立诊断面；或让聚合结果携带混合 provenance 并严格定义合并规则。

**影响。** 决定 snapshot/context/tool-result schema、当前状态 provider、动作测量和调试界面；若只在日志中保留来源，中间层可能再次把预测值无标记地升格为事实。

### SEAM-07｜同名 v1 协议发生不兼容变化时怎样演进

**证据。** TS 与 Rust 都称事件为 `mineintent.minecraft.backend-event.v1`，但 Rust 信封多了必需的 `source`，并增加 keep_alive/motor/error kinds（`materials/mineintent-main/src/minecraft/contracts.ts:214-236`、`materials/backend-rs/src/protocol.rs:27-60`）。两边也都称快照为 `mineintent.minecraft.snapshot.v1`，而 TS 把 Minecraft 版本写死为 `1.21.1`，Rust 输出 `26.1.2`（`materials/mineintent-main/src/minecraft/contracts.ts:64-76`、`materials/backend-rs/src/snapshot.rs:18-49`、`materials/backend-rs/src/snapshot.rs:341-357`）。Minecraft 线协议号 775 与这些应用协议版本是不同版本轴（`materials/backend-rs/任务书.md:48-58`）。

**选项。** 对不兼容 schema 一律升 v2；保留 v1 并通过兼容适配器把新增字段设为可选；或在连接开始先交换 capabilities/schema revisions 再选择版本。

**影响。** 决定旧 fixture 能否直接复用、strict decoding 如何配置、滚动升级是否可能，以及 snapshot/event/command/agent-context/tool-response 各自的版本策略。不能只改字符串而没有兼容与拒绝测试。

### SEAM-08｜子进程模式下怎样查询快照、块、实体与视口

**证据。** stdin 协议当前只有 send_chat/look_relative/move/release_all/respawn（`materials/backend-rs/src/protocol.rs:98-124`），而 observation API 是进程内同步读取并可直接生成完整 viewport（`materials/backend-rs/src/runtime.rs:501-580`）。

**选项。** 增加带 request id 的 query/response 信封；持续发布完整/增量状态由中间层本地缓存；或不支持生产子进程模式并采用 SEAM-01 的链接方案。

**影响。** 决定大视口消息大小、读一致性、超时、过期 epoch 检查和 fake transport 测试；这是开始 port `information/` 前的硬接缝。

### SEAM-09｜认证、身份与连接配置缺口在哪一层补

**证据。** TS 接口支持 offline/microsoft 与 profilesFolder，并分别配置 connect/login/spawn 超时（`materials/mineintent-main/src/minecraft/contracts.ts:11-24`）；Rust `RunConfig` 只有 host/port/username/worldId 等，CLI 也未提供认证模式或 profiles folder（`materials/backend-rs/src/runtime.rs:45-73`、`materials/backend-rs/src/main.rs:40-67`）。

**选项。** backend-rs 扩展 Microsoft account/profile 配置；中间层先完成账号凭据加载再把 account handle 交给后端；或本次只支持 offline，但把这是发布范围限制而非“已覆盖”写进验收门槛。

**影响。** 决定密钥存放、登录错误分类、兼容 `.env` 的范围及正式服务器可用性；任何缩小支持范围都需维护者显式接受。

### SEAM-10｜事件传输的背压、断流与恢复语义

**证据。** 进程内订阅使用 unbounded channel（`materials/backend-rs/src/runtime.rs:377-380`、`materials/backend-rs/src/runtime.rs:582-585`），跨进程输出是无握手、逐行 stdout JSON（`materials/backend-rs/src/runtime.rs:112-135`）。TS runtime 会按聊天与决策各自排队，并在 scope 变化时丢弃旧世界工作（`materials/mineintent-main/src/participant/runtime.ts:136-168`、`materials/mineintent-main/src/participant/runtime.ts:228-263`、`materials/mineintent-main/src/participant/runtime.ts:324-369`）。

**选项。** 有界 channel 加明确 overflow/fault 事件；允许丢弃高频可重建事件但绝不丢 lifecycle/chat；或持久化序列号加 resume/重放。

**影响。** 决定慢消费者、stdout 断管、事件风暴和重启时的正确性；必须区分可由新 snapshot 重建的数据与不可恢复的聊天/生命周期事实。

### SEAM-11｜命令与观察句柄是否绑定创建时的 connection epoch

**证据。** TS 在非 ready 时同步拒绝 chat/motor；observation source 固定创建时 epoch，旧连接句柄继续读取会抛 stale error，订阅也只交付同 epoch 事件（`materials/mineintent-main/src/minecraft/minecraft-backend.ts:190-241`）。Rust chat/motor/release 方法只把命令入队，未 ready 的非 respawn 命令会留到后续 tick；observation source 每次读取共享 runtime 的当前 epoch/缓存，订阅接收全部事件（`materials/backend-rs/src/runtime.rs:389-450`、`materials/backend-rs/src/runtime.rs:501-587`、`materials/backend-rs/src/runtime.rs:977-990`）。

**选项。** 所有命令和 observation handle 显式绑定目标 epoch，变化即拒绝；只允许列入白名单的 pre-ready 命令并在 ready 时绑定新 epoch；或把 Rust 句柄定义为始终指向“当前连接”的 live handle，同时另建不可混淆的 epoch-scoped API。

**影响。** 决定断线期间的 chat/move 是否可能落到重连后的世界、旧 run 是否还能读到新世界、`release_all` 是否必须越 epoch 生效，以及 stale-handle oracle 测试放在 backend 还是 adapter。

### SEAM-12｜事件发生时的 dimension 由后端信封还是中间层补齐

**证据。** TS 在生成每条事件时从 active bot 把当时 dimension 写进信封（`materials/mineintent-main/src/minecraft/minecraft-backend.ts:647-660`）。Rust 信封类型虽有可选 dimension，但构造器固定写 `None`，所有 runtime emit 都经该构造器且没有随后覆盖（`materials/backend-rs/src/protocol.rs:44-85`、`materials/backend-rs/src/runtime.rs:112-135`）。中间层用 event 的 session/epoch/world/dimension 判断聊天与声音所属 scope（`materials/mineintent-main/src/participant/runtime.ts:235-251`、`materials/mineintent-main/src/participant/information-adapters.ts:91-115`）。

**选项。** backend-rs 在事件产生点原子盖上 dimension；中间层收到事件时与同 revision snapshot 连接；或在新协议中把 scope 放进各 payload 并删除信封的含糊可选字段。

**影响。** 在 adapter 事后读取“当前 dimension”可能把切维度前的迟到事件归入新世界；改变信封则触发 SEAM-07 的协议升级和全部 scope/oracle fixture 更新。

### SEAM-13｜缺失或语义不等价的观测事实由哪一层产生和规范化

**证据。** TS observation contract 要求实体列表、三态块读取，以及实体六类、块更新/区块卸载和声音事件（`materials/mineintent-main/src/minecraft/contracts.ts:132-191`、`materials/mineintent-main/src/minecraft/contracts.ts:240-248`）；Rust 当前能读实体缓存和块/视口，但事件生产面只有 `chunk_loaded`，实体与声音只是 kind/cache（`materials/backend-rs/src/runtime.rs:274-305`、`materials/backend-rs/src/runtime.rs:539-605`、`materials/backend-rs/src/runtime.rs:993-1184`）。已有 DTO 也不全是同义转换：TS 的 self/entity key 含 epoch、alive/valid 来自 health/句柄，块属性保留原始标量且透明提示直接读取 Mineflayer；Rust 的 key 基于 UUID/ECS、alive/valid 取决于是否有 `Dead`，块属性字符串化且透明提示来自名称/轮廓启发式（`materials/mineintent-main/src/minecraft/snapshot.ts:37-114`、`materials/mineintent-main/src/minecraft/dto.ts:29-74`；`materials/backend-rs/src/snapshot.rs:214-264`、`materials/backend-rs/src/snapshot.rs:329-375`、`materials/backend-rs/src/snapshot.rs:450-519`）。聊天无 sender 时 Rust 写 null，而 TS 可选 string 要求缺席或字符串（`materials/mineintent-main/src/minecraft/contracts.ts:193-198`；`materials/backend-rs/src/runtime.rs:1086-1095`）。同名 revision 也不同义：TS lifecycle revision 只随状态 transition，Rust 随每条 lifecycle event；snapshot revision 的明确边界推进与完整状态比较/force 推进也不同（`materials/mineintent-main/src/minecraft/minecraft-backend.ts:321-348`、`materials/mineintent-main/src/minecraft/minecraft-backend.ts:405-424`、`materials/mineintent-main/src/minecraft/minecraft-backend.ts:625-632`；`materials/backend-rs/src/runtime.rs:199-203`、`materials/backend-rs/src/runtime.rs:274-308`、`materials/backend-rs/src/snapshot.rs:162-169`）。

**选项。** 由 backend-rs 直接产生缺失事件和完整快照，并把字段规范化到冻结契约；由 adapter 轮询/差分底层缓存、归并事件并显式定义 revision、丢失和转换规则；按事实种类拆分两层责任并在 fixture 中记录 provenance；或经维护者接受后版本化、缩减目标契约。

**影响。** 决定事件顺序/丢失、revision 与 epoch 身份、背压、字段 provenance、额外轮询成本以及 Paper 验收断言；若不先裁定，adapter 容易把推断值伪装成服务端事实，或让同名字段在 TS/Rust 下表达不同含义。

### SEAM-14｜复合移动方向怎样规范化

**证据。** TS 接口允许 1–4 个不重复方向，driver 对每个方向独立设置 control state，因此四种三键集合会让相反轴抵消、另一轴仍生效（例如 `forward+back+left` 保留 left）；相反二键与四键的净轴为零但仍真实按键（`materials/mineintent-main/src/minecraft/contracts.ts:257-272`、`materials/mineintent-main/src/minecraft/motor-driver.ts:33-63`）。Rust 入口也接受至多四个不重复方向，但执行层只枚举无相反键的单键/双键，其余统一成为 `WalkDirection::None`（`materials/backend-rs/src/runtime.rs:477-495`、`materials/backend-rs/src/runtime.rs:795-810`）。

**选项。** backend-rs 改为模拟四个独立按键；在公共契约层拒绝包含相反轴或超过两个方向的集合；显式定义逐轴抵消后保留另一轴；或版本化 Motor contract，并为每种组合提供固定映射表。

**影响。** 决定现有 TS 合法输入能否一比一迁移、校验错误属于哪一层、对角线/冲突键的运动结果和 Paper fixture；若静默沿用 `None`，调用成功却不移动会被上层误判为真实世界阻碍。

### SEAM-15｜首次连接请求属于哪个 attempt/epoch

**证据。** TS 在建 bot 和发送 `connection_requested` 前先增加 epoch、生成 attemptId 并进入 connecting state（`materials/mineintent-main/src/minecraft/minecraft-backend.ts:244-280`）。Rust `EventWriter` 初始为 epoch 0/`attempt-0`，`run_with_handle` 先发 `connection_requested`，到客户端 `Init` 才调用 `new_attempt()`；同一次首次连接因此跨两个身份（`materials/backend-rs/src/runtime.rs:88-107`、`materials/backend-rs/src/runtime.rs:999-1005`、`materials/backend-rs/src/runtime.rs:1246-1250`）。

**选项。** backend-rs 在发请求前预分配 attempt/epoch，并让 `Init` 消费该预留；把请求明确定义成不属于 attempt 的 pre-attempt 事件并另设信封/可空身份；由有序 adapter 缓冲后重写身份；或在协议新版本中把 request id 与 connection epoch 分开建模。

**影响。** 决定 lifecycle 排序、事件重放/去重、scope 与 stale-handle 隔离、失败发生在 `Init` 前时的归属，以及 adapter 能否无损映射 TS oracle；跨进程流若已经外发，事后重写还需要缓冲边界和失败规则。

## 四、两份视口实现

### VIEW-01｜视口算法的唯一所有者

**证据。** TS 在 `source-ports/perception.ts` 实现视锥、暴露面、0.25 格射线、实体命中盒与取消（`materials/mineintent-main/src/information/source-ports/perception.ts:92-160`、`materials/mineintent-main/src/information/source-ports/perception.ts:310-527`），provider 再固定 70°/16:9、32 格、256 方块和 8 实体并组成模型 DTO（`materials/mineintent-main/src/information/providers/viewport-provider.ts:38-50`、`materials/mineintent-main/src/information/providers/viewport-provider.ts:87-110`）。backend-rs 已有同参数的投影和相同输出形状（`materials/backend-rs/src/viewport.rs:1-68`、`materials/backend-rs/src/viewport.rs:101-165`）。

**选项。**

1. backend-rs 的 viewport 成为唯一生产实现，Rust 中间层 provider 只做信息契约/权限/DTO 映射。
2. backend-rs 只提供 raw observation，视口算法作为中间层模块由 TS 机械移植；后端副本退为对照测试。
3. 抽出独立共享 viewport crate，backend 与中间层只通过明确 trait 使用它。

**影响。** 选 1 最少重复但会把产品感知参数下沉到后端；选 2 保持信息层所有权但重复已验收工作、跨进程时读取成本高；选 3 边界最清楚但需要仓库/发布/依赖版本设计。无论哪项，TS 的逐条几何与 provider 断言都仍需成为同一实现的回归 oracle。

### VIEW-02｜视口 revision、来源与取消由谁封装

**证据。** TS provider 每次投影都发新 revision，因为 backend snapshot revision 不随每次方块/实体变化推进（`materials/mineintent-main/src/information/providers/viewport-provider.ts:112-133`）；Rust `viewport()` 返回 projection，但来源要另读 `snapshot_source()`（`materials/backend-rs/src/runtime.rs:526-567`）。TS 扫描还在密集循环中让出事件循环并检查取消，相关实现位于 `materials/mineintent-main/src/information/source-ports/perception.ts:113-132` 与 `materials/mineintent-main/src/information/source-ports/perception.ts:266-308`。

**选项。** provider 继续签发“每次读取唯一”的 projection revision；后端提供原子 `{projection, source, revision}`；或建立真正随可见内容变化的 revision 流。

**影响。** 决定 stale read 检测、缓存、分页/ref 绑定、Rust CPU 任务取消和同 scope 一致性；若来源与投影分两次读取，还需定义两次读取间发生 world/epoch 变化时如何拒绝结果。

## 五、Python Agent Service 边界（本次不移植其实现）

任务书要求 Python 测试标注为 agent 层、本次移植不动（`任务书.md:19-22`）；以下只问 Rust 中间层怎样与它接缝。

### AGENT-01｜保留双向 loopback HTTP 还是改传输

**证据。** 当前中间层向 Python `POST /v1/decide`/`/v1/cancel`，同时临时监听 `POST /v1/tool` 供 Python 回调；两边各用独立令牌，URL 只允许无凭据 loopback HTTP（`materials/mineintent-main/src/models/agent-service-client.ts:30-105`、`materials/mineintent-main/src/models/agent-service-client.ts:108-132`、`materials/mineintent-main/src/models/tool-bridge.ts:5-17`、`materials/mineintent-main/src/models/tool-bridge.ts:45-66`）。

**选项。** Rust 原样重建双向 HTTP；改为一条双向长连接/本地 socket；或保留 Python HTTP 端点但由 Rust 建单一 gateway 隔离内部工具分派。

**影响。** 原样保留最利于机械迁移测试；改传输需要同步修改本次范围外的 Python 服务及其全部测试，并重新定义认证、断线和并发 run 语义。

### AGENT-02｜谁负责启动、监督与关闭 Agent Service

**证据。** 当前 Node 不启动 Python，启动时也不预检服务；用户需先单独启动 Python（`materials/mineintent-main/docs/architecture.md:22-27`、`materials/mineintent-main/docs/guides/run.md:53-73`）。App 只装配客户端、tool bridge、debug server 与 runtime，并按本地资源逆向关闭（`materials/mineintent-main/src/app/mineintent-app.ts:19-58`、`materials/mineintent-main/src/app/mineintent-app.ts:61-82`）。

**选项。** 继续由外部进程管理器负责；Rust app 启动并监督 Python child；或提供两种显式运行模式。

**影响。** 决定健康检查、日志归属、崩溃重启、环境/密钥继承和 shutdown 顺序；若 app 监督，必须避免把 Agent Service 重启误判为 AI/世界身份变化（Q06/Q11）。

### AGENT-03｜Agent 协议版本由谁协商、哪些限制属于 wire contract

**证据。** 当前边界固定 agent-context.v3、agent-run.v1、tool-response.v2，并严格限制响应大小、回调 URL/令牌和取消时限（`materials/mineintent-main/src/models/agent-service-client.ts:5-28`、`materials/mineintent-main/src/models/agent-service-client.ts:39-105`、`materials/mineintent-main/src/models/tool-bridge.ts:7-10`）。Python 还固定每 run 16 次模型请求、每响应 8 个工具、每 run 32 个工具和 180 秒期限（`materials/mineintent-main/agent-service/server.py:26-38`、`materials/mineintent-main/agent-service/server.py:511-613`）。

**选项。** Rust 完全复现既有版本与限制；增加 `/capabilities` 或请求头协商后再升级；或由部署配置锁定成对版本并在启动时 fail-fast。

**影响。** 决定旧 Python 能否无改动配合新中间层、滚动升级方式，以及大小/次数/期限测试应归 Rust transport 还是保留在 Python agent 层。

### AGENT-04｜tool-call 一次性与 observationAfter 的权威状态放哪一侧

**证据。** Node 在执行前认领 `(runId, toolCallId)`，重复调用不会再次产生副作用，并在工具处理后采样 observation（`materials/mineintent-main/src/participant/runtime.ts:176-225`、`materials/mineintent-main/src/app/mineintent-app.ts:28-35`）。Python 也拒绝同一 run 内重复 tool call id，并把 `{result, observationAfter}` 放进 tool message（`materials/mineintent-main/agent-service/server.py:445-470`、`materials/mineintent-main/agent-service/server.py:556-600`）。

**选项。** Rust runtime 保持唯一权威 claim、Python 只作早期拒绝；把幂等键持久化到 bridge；或规定 run 生命周期内存级一次性并明确重启即失败整个 run。

**影响。** 决定 callback 重试、进程崩溃恢复和 exactly-once/at-most-once 的真实承诺；不能仅依靠 Python 已见集合保护世界副作用。

## 六、持久化、配置与验收接缝

### MIG-01｜旧数据文件的兼容、迁移与回滚

**证据。** 当前 app 固定使用 `memories.json` 与 `events.jsonl`（`materials/mineintent-main/src/app/mineintent-app.ts:24-27`），memory 使用 memory-file.v1 整文件重写，journal 使用 event.v1 追加 JSONL（`materials/mineintent-main/src/memory/memory-store.ts:7-14`、`materials/mineintent-main/src/memory/memory-store.ts:70-75`、`materials/mineintent-main/src/events/journal.ts:5-35`）；Python 另写 agent-transcript.v1 并在约 32 MiB 时轮转（`materials/mineintent-main/agent-service/server.py:624-672`）。

**选项。** 原地升级并先备份；写入新目录/新版本、成功后切换；双读单写过渡；或只提供离线迁移工具。

**影响。** 决定崩溃一致性、文件权限、降级可行性、重复导入检测和用户如何验证迁移；长期记忆还受 DELTA-01/Q12 的前置裁定约束。

### MIG-02｜环境变量与部署兼容到什么程度

**证据。** TS app 读取 world/host/port/username/auth/profile、data/debug、Agent Service URL/token，并把 Minecraft 版本固定为 1.21.1（`materials/mineintent-main/src/app/config.ts:5-40`）；Python 独立读取模型配置，示例明确 Node 不使用这些变量（`materials/mineintent-main/.env.example:14-27`）。Rust backend CLI 当前只有 host/port/username/world-id/duration/reconnect-delay/send-chat（`materials/backend-rs/src/main.rs:40-67`）。

**选项。** 新 Rust app 保持现有 `MINEINTENT_*` 名称并拒绝无效旧值；发布一次显式配置格式迁移；或同时支持 env 与配置文件并定义优先级。

**影响。** 决定无停机替换、密钥泄漏面、配置 strictness 测试和 1.21.1 → 26.1.2 的失败提示；不能静默忽略旧变量。

### MIG-03｜只读调试接口是否保持 HTTP/JSON 兼容

**证据。** 当前 debug server 只绑定 127.0.0.1，只接受 GET，并提供 `/health` 与 `/v1/state`（`materials/mineintent-main/src/telemetry/debug-server.ts:4-12`、`materials/mineintent-main/src/telemetry/debug-server.ts:17-40`）。

**选项。** 原样兼容 endpoint/schema；保留 endpoint 但升 debug-state 协议；或改成仅本地 socket/CLI 并提供转换工具。

**影响。** 决定现有运维脚本、状态脱敏测试与诊断体验；若 schema 变化，需与产品/世界事实来源字段一起版本化。

### MIG-04｜何种证据构成中间层移植完成

**证据。** 任务书把 TS 实现/测试定为 oracle，并要求测试逐条对应、保留断言语义（`任务书.md:5-6`）。当前快速测试不启动 Minecraft，现有 Paper 场景不启动 Agent Service/真实模型，也不验证聊天、关系、记忆或工具循环；仓库没有可重复的真实模型纵向验收（`materials/mineintent-main/docs/guides/validation.md:20-27`、`materials/mineintent-main/docs/guides/validation.md:34-43`、`materials/mineintent-main/docs/guides/validation.md:112-124`）。

**选项。** 在全部 `src/` 模块完成移植的固定前提下，把自动化门槛设为全部 TS 测试逐条 Rust 对应 + backend 既有 M0-M6；再追加 Rust middle + Python fake provider + backend fake 的纵向测试；或再要求 Paper + Python + 指定真实模型的可重复场景。

**影响。** 决定 CI 资源、密钥/模型可重复性、artifact 脱敏与“完成”能声称的范围。各层证据可以分级，但维护者需要明确最终 gate，不能用窄单元测试证明完整闭环。
