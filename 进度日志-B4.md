# B4 进度日志：生产 capability / registry-backed dispatcher

## 实现边界

本批完成 Participant Runtime 之前可独立验收的 middle capability 层：

- `ToolCapabilityRegistry` 以同一注册 Vec 同时派生 definitions、resolve 与 dispatch，生产顺序固定为 `look_relative`、`move_input`、`view`、`say`、`remember`；重复名称在构造时返回 `duplicate_tool_capability`。
- `RegistryToolDispatcher` 使用显式 `CapabilityInvocationAssembler`（action id、UTC startedAt）、显式 world/chat/scope assembly、传入的 `ExecutionControl` 与现有 `ExecutionArbiter`。lease 由 Drop guard 释放，scope invalidation 与 cleanup 失败都不会永久占用 tool gate。
- `observationAfter` 是显式 `ObservationAfterSource` seam。dispatcher 只在 registry 解析出的 `ExecutionResource::Body` 上调用一次；身体成功/普通失败都可注入不含 viewport 的事实，View/Chat/Memory 永远直接返回 null。
- body capability 只通过 `MinecraftMotorDriverApi` future 执行动作，并用调用前后 `ProtocolObservationSource::self_pose` 计算 `look_relative`/`move_input` effect。结果不嵌入 viewport；唯一显式 viewport 读取仍是 B3 的 `ViewportReader`/`view`。
- `say` 保持 `text` 最多 500 Unicode scalar、trim 后非空、scheduler segments、action id 作为 speech request id、`queued` 语义和 journal 正文脱敏。scheduler 已成功排队后，普通 journal 失败不撤回 queued 结果；控制/作用域失效仍结构化传播。
- `remember` 使用 Issue #127 的单文本 `append`、唯一非空锚点 `replace`（`newText: ""` 表示删除）和 `rewrite`。MemoryStore 负责当前全文、串行编辑和滚动备份；模型成功结果保持 frozen 最小 `{protocol,status}`，operation 只在脱敏 journal metadata 中出现。

未修改 frame/opening frame、backend-event v1/v2、SEAM-10/13、light、Participant Runtime、app/composition root 或 concrete backend facade。

## 控制、资源与错误证据

具名 `capability_dispatch` 测试覆盖：Body 成功/普通失败 seam 计数、非 Body `view`/`say`/`remember` 零 seam 调用、busy 有界等待、取消后的 lease 释放、cleanup `release_all` 失败、unknown/cancel/deadline/scope、严格参数零副作用及每项 capability 的普通失败。阻塞测试均用 `Notify`/completion 状态和最长 1 秒 timeout；没有无限 join。

`AgentLoopDriver` 将 `ScopeInvalid` 与 cancellation/deadline 一样继续传播；普通 dispatcher error 仍通过已有 paired tool-result 路径回放。普通摘要在 capability、dispatcher 和 AgentRun local-failure 路径均清理控制字符并限制为最多 300 Unicode scalar。

## Mutation 证据
